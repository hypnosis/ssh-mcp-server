# Баг-репорт приёмки перед v2.0.0

Приёмка ветки `feat/openssh-transport` (worktree `core11`): каждый инструмент вызывается по
MCP так, как его вызовет клиент. Стенды — `mcp-alpine` (BusyBox), `mcp-debian` (coreutils),
`mcp-router` (dropbear без sftp), `zabegaika` (реальный сервер, песочница
`/root/ssh-mcp-acceptance`).

Здесь только находки. Починки — отдельным заходом после код-ревью.

Сырые ответы: `<scratchpad>/acceptance/logs/*.jsonl`, идентификатор кейса — поле `id`.
Всего сделан **251 вызов** по MCP. Каждый инструмент из четырнадцати вызван хотя бы на трёх
стендах. После приёмки следы убраны со всех серверов, песочница на реальном сервере снесена.

**Итог приёмки: два блокера** (AC-10 — снимок вешает сервер; AC-18 — доступ без учётных
данных по чужому соединению), десять важных находок и шесть мелочей.

Затем прошло код-ревью тремя агентами — не по диффу, а по классам найденных дефектов. Оно
добавило ещё **четыре важных находки и восемь мелочей** (AC-20…AC-31, отдельный раздел ниже).
Всё, что ревьюеры утверждали, перепроверено по коду, а где возможно — живым замером;
неподтверждённое в список не включено. Корень AC-10, предложенный ревью, замером при починке
опровергнут — настоящая причина разобрана в самой находке.

### AC-18 — профиль без ключа входит по чужому общему соединению

Инструмент: транспорт (виден через `ssh_exec`) · Стенд: debian · Серьёзность: **блокер**
Кейсы: G05, S1 (`logs/group-g.jsonl`, `logs/steal.jsonl`), воспроизведено дважды

Профиль в файле, у которого нет ни `privateKeyPath`, ни `password`:

```json
"lab-nocreds": { "host": "127.0.0.1", "port": 2232, "username": "root",
                 "strictHostKeyChecking": "no", "ignoreUserConfig": true }
```

Ожидание: отказ по аутентификации. Сам по себе он его и получает — проверено при закрытом
общем соединении (G23, G33, G40): `Authentication failed … Permission denied
(publickey,password)`.

Факт: если общее соединение к `127.0.0.1:2232` под пользователем `root` уже поднято **другим
процессом сервера** (законным профилем со своим ключом), тот же вызов выполняется:

```
[S1] ok 28ms — профиль без ключа при мастере от другого процесса
    root ПРОШЁЛ
```

Команда выполнена от root. Ключ при этом контейнером не принимается: личный ключ
пользователя проверен вручную — `Permission denied` (G25), в ssh-агенте ключей нет (G24).

Причина в коде: `src/runner/ssh-args.ts:121` — путь общего сокета строился как
`%C`, то есть хэш от (локальный хост, удалённый хост, порт, пользователь). Ни ключ, ни имя
профиля, ни правила профиля в него не входят. Сокет живёт `ControlPersist` (по умолчанию
600 c) и общий для всех процессов — это заявленное свойство проекта, ради него всё и
затевалось.

Следствие: любой профиль в файле, совпадающий по трём полям `host`/`port`/`username`,
работал без собственных учётных данных, пока жив чужой сокет. Ограничения такого профиля
(другой ключ, свой `pathSecurity`) при этом оставались на месте, но сам доступ — нет.

**Исправлено.** Имя сокета считается самим проектом: хэш от назначения и отпечатка учётных
данных (`ssh-args.ts:141`). Профили с одинаковыми учётными данными по-прежнему делят
соединение, профиль с другими — получает своё. Тот же отпечаток вошёл в ключ кэша
транспортов (`openssh-runner.ts:513`), иначе профиль без ключа получал бы чужой транспорт
внутри одного процесса. Замер повторён: при живом чужом мастере профиль без учётных данных
получает `Authentication failed … Permission denied`, законный профиль из третьего процесса
ходит по тому же мастеру за 33 мс. Длина пути сокета — 55 байт при лимите 104.

### AC-19 — вход по чужому соединению закрывает его за собой

Инструмент: транспорт · Стенд: debian · Серьёзность: важно
Кейсы: S1→S2 (дважды), контроль L1→L2 (`logs/steal.jsonl`, `logs/legit.jsonl`)

Факт: после команды профиля без ключа общее соединение мертво —
`Master: ❌ not running`, хотя до вызова было `Master: ✅ active (PID 43162)`.

Контроль: та же последовательность с законным профилем из другого процесса соединение не
трогает — `Master: ✅ active (PID 43162)` и после команды.

То есть неудачная (по смыслу) попытка рвёт канал, которым пользуется соседнее окно, — ровно
то, чего проект избегает сознательно: на выходе соединения не закрываются, чтобы не мешать
другим.

**Где в коде закрывался чужой мастер** (найдено код-ревью, проверено по коду):

- `src/runner/openssh-runner.ts:551-553` — при несовпадении отпечатка учётных данных код
  закрывал существующее соединение: «credentials changed, closing the existing master
  connection». Отпечаток локальный, а сокет — общий для всех процессов, так что закрывался
  канал, который поднял кто-то другой.
- `src/tools/monitoring-tool.ts:216-234` — действие `close` инструмента `ssh_monitor` шлёт
  `-O exit` на общий сокет, не спрашивая, кто его поднял.
- `src/runner/ssh-args.ts:222-233` — `buildControlArgs` строит и `-O exit`, и `-O check` на
  том же пути, слепом к учётным данным.

**Исправлено вместе с AC-18.** Сокет теперь свой у каждого набора учётных данных, поэтому
чужой канал недостижим: вытеснение при смене отпечатка убрано за ненадобностью, а `-O exit`
и `-O check` попадают на собственный путь. Замер: после попытки профиля без учётных данных
мастер законного профиля остаётся `✅ active`; `ssh_monitor close` по alpine не трогает
соединение debian.

### AC-10 — снимок вешает сервер, если соединение ещё не поднято

Инструмент: `ssh_snapshot` · Стенд: alpine, debian, router, zabegaika · Серьёзность: **блокер**
Кейсы: E01–E04, S01–S06, S10–S12, S20 (`logs/group-e.jsonl`, `logs/snapshot-*.jsonl`)

Вызов: `{"profile": "lab-debian"}` — первым обращением к профилю в свежем сервере.

Ожидание: снимок за секунды. Он состоит из десяти чтений вроде `hostname`, `uptime -p`,
`free -h`; каждое из них, выполненное вручную по ssh, отвечает мгновенно (замерено).

Факт: ответа нет вообще. Ждали 180 с (E01–E04, все четыре стенда), 40 с и 25 с в отдельных
замерах — тишина. Дальше **сервер уже не отвечает ни на что**: следующий `ssh_exec` с той же
пустой командой тоже висит (S11), и следующий снимок тоже (S12). Единственный выход —
перезапуск процесса.

Условие воспроизведения — непрогретое соединение:

| Порядок вызовов | Результат |
|---|---|
| `ssh_snapshot` первым | зависает навсегда, сервер мёртв (S10, S20) |
| `ssh_exec` → `ssh_snapshot` | снимок за **183 мс** (S01, S02) |
| `ssh_monitor close` → `ssh_snapshot` | зависает снова (S03, S04) |

Что видно в подробном логе (`logs/snapshot-diag.stderr.log`): десять чтений стартуют
одновременно, следом десять одинаковых строк `[Runner] OpenSSH_10.2p1 …, multiplexing: on`
в одну миллисекунду — и лог обрывается. Ни одного процесса `ssh` в это время в системе нет
(замерено на t+3, t+8, t+15 с) — значит висит собственный код, ещё до запуска клиента.

Инструмент `ssh_snapshot` — единственный, кто запускает десять чтений через `Promise.all`
(`src/tools/snapshot-tool.ts:63-74`), поэтому и виден на нём первым.

**Корень — взаимная блокировка шлюза и паспорта** (установлен замером при починке; версия
про гонку кэшей, стоявшая здесь раньше, замером опровергнута — см. ниже).

Десятое чтение снимка идёт с `sudo` (`src/tools/snapshot-tool.ts:304`, ошибки из syslog).
Из-за `sudo` executor первым делом спрашивает паспорт сервера
(`src/managers/ssh-executor.ts:94`), а проба паспорта уходила на сервер обычным `exec`
(`ssh-executor.ts:159`) — то есть **через шлюз первой команды**. Остальные девять чтений к
этому моменту уже закрыли шлюз и внутри себя ждут тот же паспорт
(`src/runner/openssh-runner.ts:372`). Круг замкнут: шлюз ждёт паспорт, паспорт ждёт шлюз,
до `runProcess` дело не доходит — потому в системе и нет ни одного процесса `ssh`.

Собственная проба транспорта этой ловушки избегала: она ходит `execOnce`, мимо шлюза
(`openssh-runner.ts:388`). Разошлись две реализации одной пробы — в этом весь дефект.

Что показали контрольные замеры (по одному режиму на запуск, поверх сборки, вне MCP):

| Режим | Итог |
|---|---|
| десять команд прямо через транспорт | 10/10 за ~120 мс |
| девять чтений через executor, без `sudo` | 9/9 за ~110 мс |
| одна команда с `sudo`, без залпа | 1/1 за 30 мс |
| **кэш транспорта прогрет заранее** (гонки нет) **+ залп с `sudo`** | **0/10, висит** |

Последняя строка и опровергает прежнюю версию: с одним экземпляром транспорта зависание
воспроизводится ровно так же. Отдельно проверено, что дубля транспорта нет и без прогрева:
`runnerCache` читается и пишется в одном синхронном участке после `await`, поэтому
опоздавшие находят готовую запись даже когда обнаружение отвечает вразнобой. Десять
одинаковых строк `[Runner] …` в логе — отпечаток гонки в `detectRuntime`
(`src/runner/runtime-check.ts:162-186`), а не десять экземпляров транспорта.

**Исправлено.** Паспорт для инструментов берётся у транспорта, где проба идёт мимо шлюза;
`passport()` вынесен в контракт `CommandRunner`. Отдельно закрыта гонка обнаружения:
`detectRuntime` кэширует сам вызов, а не результат. Живая проверка — снимок первым вызовом
на alpine (234 мс), debian (297 мс), router (192 мс), после каждого `ssh_exec` отвечает;
строка `[Runner] …` в логе одна. Сторож — `tests/unit/executor-passport-gate.test.ts`.

### AC-14 — невыполненные разделы аудита выглядят как проверенные

Инструмент: `ssh_audit_baseline` · Стенд: debian · Серьёзность: важно
Кейс: F11 (`logs/group-f.jsonl`)

Вызов: `{"include": ["disk", "mem"]}` — просили два раздела.

Ожидание: в отчёте два раздела, остальных нет.

Факт: отчёт полный, а невыбранные разделы заполнены значениями, которые читаются как
результат проверки:

```
services: running=0, failed=0
docker: not installed or not accessible
firewall: ufw_active=false, iptables_rules=0
updates:  upgradable=0, reboot_required=false
```

Ни одна из этих проверок не выполнялась. «Файрвол не активен, правил 0, обновлений 0» —
это утверждения о сервере, а не признание, что раздел пропущен. В том же ответе `host`,
`os`, `kernel` пусты, а `raw JSON` содержит `"hostname": ""`.

Механизм честного признания в инструменте есть и работает — в этом же ответе стоит
`NOT CHECKED: listeners (neither ss nor netstat on the server)`. На пропущенные по выбору
разделы он не распространён.

**Исправлено.** Отчёт печатает только запрошенные разделы: поля, которых нет в `include`,
не появляются ни в сводке, ни в JSON. Отсутствие поля и значит «не спрашивали».
Замер: `{"include": ["disk", "mem"]}` на debian — в ответе диск, память и ничего больше.

### AC-15 — неизвестный раздел в `include` проглатывается молча

Инструмент: `ssh_audit_baseline` · Стенд: debian · Серьёзность: важно
Кейс: F12 (`logs/group-f.jsonl`)

Вызов: `{"include": ["нет-такого-раздела"]}`

Ожидание: отказ с перечислением доступных разделов — их девять, и они названы в схеме.

Факт: обычный отчёт, где всё пусто или в нулях, плюс те же `firewall: ufw_active=false`,
`updates: upgradable=0`. Опечатка в имени раздела превращается в отчёт «сервер чист».

**Исправлено.** Имена сверяются со списком разделов до первой команды:
`Unknown audit section(s): нет-такого-раздела. Available: system, disk, mem, net, ssh,
services, docker, firewall, updates.` На сервер при этом не уходит ничего.

### AC-16 — в разбор диска протекают служебные разделители

Инструмент: `ssh_disk_breakdown` · Стенд: все · Серьёзность: мелочь
Кейсы: F20, F21, F26 (`logs/group-f.jsonl`)

Факт: ответ начинается с `__SSH_MCP_DISK_SEP__df__SSH_MCP_DISK_SEP__` и содержит такие же
метки перед каждым блоком (`__SSH_MCP_DISK_SEP__du_/tmp__SSH_MCP_DISK_SEP__`). Внутренний
способ разрезать вывод показан пользователю как часть отчёта.

Сами данные при этом верные, а `paths` работает: при `{"paths": ["/tmp", "/var"]}` в ответе
именно эти два дерева.

### AC-17 — сырые сообщения systemctl подставляются как значения полей

Инструмент: `ssh_service_status` · Стенд: zabegaika, debian · Серьёзность: мелочь
Кейсы: F30, F32 (`logs/group-f.jsonl`)

Факт для несуществующей службы:
`enabled: Failed to get unit file state for no-such-unit.service: No such file or directory`
— текст ошибки стоит на месте значения поля. Ниже отчёт продолжается как обычно:

На стенде без systemd (F30) — `enabled: enabled` рядом с `active: ?/?` и текстом

знаками вопроса, общего вывода «судить нечем» нет.

### AC-11 — занятость памяти в снимке посчитана неверно

Инструмент: `ssh_snapshot` · Стенд: zabegaika · Серьёзность: важно
Кейс: E41 (`logs/group-e2.jsonl`)

Факт: `Memory: 506Mi / 3.8Gi (13316% used)`. На debian, где обе величины в одних единицах,
счёт верный: `2.8G / 7.7G (36% used)`. Единицы `Mi`/`Gi` (их отдаёт `free -h` на свежих
coreutils) при делении не приводятся друг к другу.

Цифра из снимка попадает прямо в отчёты — «13316% памяти занято» читается как авария там,
где занято 13%.

**Исправлено.** Размеры приводятся к байтам по суффиксу (`Ki`/`Mi`/`Gi` у coreutils,
`K`/`M`/`G` у BusyBox — и то и другое степени 1024), и только потом делятся; неразобранный
вывод даёт `usage NOT CHECKED`, а не ноль. Замер на alpine с подставленным `free`
(`3.8Gi` всего, `506Mi` занято): `Memory: 506Mi / 3.8Gi (13% used)`.

### AC-12 — в снимке «проверить нечем» показано как «ничего нет»

Инструмент: `ssh_snapshot` · Стенд: alpine, router · Серьёзность: важно
Кейсы: E21, E31 (`logs/group-e2.jsonl`)

Факт на BusyBox-стендах:

```
SERVICES
  No active services detected
NETWORK
  Established connections: 0
  Listening ports:
```

При этом на стенде работает sshd и слушает порт 22 — просто `systemctl`, `ss` и `netstat`
там отсутствуют. Инструмент выводит запасное значение молча, и «нечем проверить»
превращается в утверждение «служб нет, портов нет».

Uptime в том же снимке подан честно (`Uptime: unknown`, потому что `uptime -p` BusyBox не
знает) — то есть honest-ветка в инструменте есть, но применена не везде.

**Исправлено.** Наличие `systemctl` проверяется до опроса служб, а список слушателей идёт
с маркером `NO_NET_TOOL`. Ответ на BusyBox-стенде: `NOT CHECKED: no systemctl on the
server` и `NOT CHECKED: neither ss nor netstat on the server`.

Заодно нашлась потеря: прежний конвейер `ss … || netstat …` до запасного `netstat` не
доходил никогда — `sort` в конце конвейера возвращает ноль и при отсутствии `ss`. Теперь
команда выбирается явно, и на alpine с router в снимке виден слушающий порт 22.

### AC-01 — таймаут срабатывает на 5 секунд позже заявленного

Инструмент: `ssh_exec` · Стенд: alpine, debian, router · Серьёзность: важно
Кейсы: A09, A10, A17 (`logs/group-a.jsonl`)

Вызов: `{"command": "echo started; sleep 30", "timeout": 3000}`

Ожидание: ответ примерно через 3 c — столько названо в параметре.

Факт: 8016 мс (debian), 8045 мс (alpine), 8032 мс (router). Текст ответа:
`Error: Command timed out after 3000ms on root@127.0.0.1:2232.`

Причина видна в коде: по истечении срока процессу шлётся `SIGTERM`, и `ssh` его не
отрабатывает, пока висит удалённая команда; выход происходит по `SIGKILL` через
`DEFAULT_KILL_GRACE_MS = 5000` (`src/runner/process.ts:16,133-140`). Клиенту при этом
сообщается срок 3000 мс — сообщение и поведение расходятся.

**Исправлено, причина была другой.** Замер показал: `ssh` умирает по `SIGTERM` за три
миллисекунды, а событие `close` приходит через тридцать секунд — когда заканчивается
удалённая команда. Потоки убитого клиента держит общий master-процесс, унаследовавший те
же дескрипторы; ответ поэтому упирался в срок сторожа на сервере, а не в запас перед
`SIGKILL`. Теперь убитый нами процесс дожидается своей смерти, а не закрытия чужих потоков:
8123 → 3231 мс (debian), 8117 → 3218 (alpine), 8071 → 3220 (router).

### AC-04 — про сверку sha256 клиенту не говорят ничего

Инструмент: `ssh_file_write` · Стенд: alpine, debian, router · Серьёзность: важно
Кейсы: B03, B04, B05, B31 (`logs/group-b.jsonl`, `logs/group-b-noverify.jsonl`)

Ожидание: три исхода сверки различимы в ответе — сошлось, не сошлось, проверить нечем
(инвариант «честный ответ», CLAUDE.md §7).

Факт: ответ во всех случаях один и тот же — `File written successfully: <путь>`. Он же

### AC-07 — `owner` без `sudo` не применяется и об этом молчат

Инструмент: `ssh_upload` · Стенд: debian · Серьёзность: важно
Кейсы: C37, C42 (`logs/group-c2.jsonl`, `logs/group-c3.jsonl`)

Вызов: `{"local_path": "…/small.txt", "remote_path": "/tmp/xfer/owner-test.txt",

Факт: `✓ Upload OK: /tmp/xfer/owner-test.txt … (verified)`. Владелец файла на сервере —

**Исправлено.** Пропуск назван в ответе:
`warnings: - owner was NOT applied: chown needs sudo — the file belongs to the connecting
user`. Замер на debian: файл по-прежнему `root:root` (передача идёт под root), но об этом
теперь сказано; с `sudo: true` тот же вызов даёт `daemon:daemon` и молчит.

### AC-20 — аудит SSH молчит о небезопасной настройке, если не смог её прочитать

Инструмент: `ssh_audit_baseline` · Стенд: debian · Серьёзность: важно
Кейсы: R10, R11 (`logs/review-probe2.jsonl`)

Один и тот же сервер, один и тот же профиль (непривилегированный `deploy`), разница только
в флаге:

| Вызов | Что в отчёте |
|---|---|
| `{"include": ["ssh"]}` | `sshd: port= root= pwauth= pubkey=`, красных флагов нет |
| `{"include": ["ssh"], "include_sudo_sections": true}` | `CRITICAL: PasswordAuthentication yes on port 22` |

Настройка сервера всё это время одна и та же (`sshd -T`: `passwordauthentication yes`,
`port 22`). Без флага команда идёт без sudo (`src/tools/audit-tool.ts:247` —
`useSudo = include.includes('ssh') && !!args.include_sudo_sections`), вывод пуст, поля
пустые, а проверка красных флагов на пустой строке даёт «всё хорошо»
(`audit-tool.ts:362-366`, `/^yes$/i.test('')` → `false`).

Пустой раздел при этом **не попадает** в `NOT CHECKED` — этот список собирается только для
диска и слушателей (`audit-tool.ts:289-292`).

Аудит безопасности, который молчит именно там, где не смог посмотреть, опаснее отсутствия
аудита.

**Исправлено.** Пустой `sshd -T` больше не разбирается: раздел уходит в `NOT CHECKED` с
подсказкой, красные флаги по пустым полям не считаются. Замер под `deploy`:
`NOT CHECKED: sshd config (sshd -T gave no output — run with include_sudo_sections: true)`;
с флагом — прежний `CRITICAL: PasswordAuthentication yes on port 22`.

### AC-21 — загрузка процессора в снимке на BusyBox — произвольное число

Инструмент: `ssh_snapshot` · Стенд: alpine, router · Серьёзность: важно
Кейс: E21 (`logs/group-e2.jsonl`), прямой замер команды

Факт: снимок BusyBox-стенда показал `CPU: 18 cores, 233.0% used`, тогда как машина
простаивала (`top`: `100% idle`, load average 1.05 на 18 ядер).

Команда снимка `top -bn1 | grep "Cpu(s)" | awk '{print $2}' | cut -d"%" -f1`
(`src/tools/snapshot-tool.ts:186-190`) рассчитана на формат procps. У BusyBox строка
называется `CPU:  0% usr  0% sys …`, и `grep "Cpu(s)"` цепляет случайные строки таблицы
процессов: прямой запуск на стенде вернул `74` и `76` — это и уезжает в отчёт как проценты.
На coreutils та же команда даёт верное `0.0`.

**Исправлено.** Сводная строка разбирается на нашей стороне, а не вырезается колонкой:
занятость считается от доли простоя, которая есть в обоих форматах (`95.1 id` у procps,
`99% idle` у BusyBox). Строки не нашлось — `usage NOT CHECKED`, а не число.
Замер: alpine `1.0% used`, router `0.0% used`, реальный сервер `31.8% used`.

### AC-22 — «файрвол выключен» на сервере, где файрвола нет вовсе

Инструмент: `ssh_audit_baseline` · Стенд: alpine · Серьёзность: важно
Кейсы: R20, R21 (`logs/review-probe3.jsonl`)

На стенде не установлены ни `ufw`, ни `iptables` (проверено). Команда раздела возвращает
литерал `NO_UFW` (`audit-tool.ts:235`), а отчёт печатает
`firewall: ufw_active=${/Status: active/.test(...)}` (`audit-tool.ts:515`) — то есть
`ufw_active=false`, ровно то же, что у сервера с установленным и выключенным ufw.

**Исправлено.** У каждого экрана три исхода: не установлен, не дали посмотреть, посмотрели.
Команда раздела сама различает их (`command -v` вместо погашенной ошибки), отчёт печатает
`firewall: ufw=not installed, iptables=not installed`, а «посмотреть не дали» попадает ещё
и в `NOT CHECKED`. Пустой счётчик правил iptables теперь тоже «нечем проверить»: даже на
машине без единого правила команда печатает заголовки цепочек.

### AC-23 — `owner` не применяется и к каталогам (дополнение к AC-07)

Инструмент: `ssh_upload` · Стенд: debian · Серьёзность: важно
Кейсы: R13, R14 (`logs/review-probe2.jsonl`)

Вызов: `{"local_path": "…/tree", "remote_path": "/tmp/owner-tree", "recursive": true,

Факт: ответ `✓ Upload OK … sha256: verified (3 files)`, на сервере

Рекурсивная отправка под `sudo` при этом честно отказывает: «Recursive sudo upload is not

### AC-24 — исчезнувший раздел ошибок читается как «ошибок нет»

Инструмент: `ssh_snapshot` · Стенд: все · Серьёзность: мелочь

Чтение `/var/log/syslog` завёрнуто в `try`, любое исключение проглатывается, список ошибок

### AC-25 — сбой проверки существования читается как «файла нет»

Инструмент: `ssh_upload` · Стенд: все · Серьёзность: мелочь

`remoteExists` ловит любое исключение и возвращает `false`. При `overwrite: false` это

### AC-26 — «доступно памяти» может оказаться размером кэша

Инструмент: `ssh_audit_baseline` · Стенд: старые системы · Серьёзность: мелочь
Код: `src/tools/audit-tool.ts:411-420`

`available: c[c.length - 1]` — берётся последняя колонка строки `Mem:`. На `free` из procps
старше ~2014 (CentOS 6, встраиваемые сборки) колонки `available` нет вовсе, и последней
идёт `cached`. Отчёт покажет объём кэша под именем «доступно».

**Исправлено.** Показатели читаются по именам колонок заголовка. Замер на debian с
подложенным старым `free`: было `avail=3.4G` при 800M свободной памяти, стало `avail=n/a`.

### AC-27 — том с длинным именем исчезает из отчёта о дисках

Инструмент: `ssh_audit_baseline` · Стенд: серверы с docker/NFS · Серьёзность: мелочь
Код: `src/tools/audit-tool.ts:396` — `if (cols.length < 7) continue;`

`df -hT` переносит запись на две строки, если имя файловой системы длинное (overlay-пути
docker, длинные NFS-адреса): в первой одна колонка, во второй шесть. Обе отбрасываются, том
пропадает из раздела молча — ни в `NOT CHECKED`, ни в красных флагах.

**Исправлено, причина оказалась другой.** Замер на подложенном выводе показал: вторая
половина выровнена пробелами, при разбиении получалось пустое первое поле — ровно на месте
пропавшего имени, и запись доезжала целиком, но с пустым `filesystem`. Первая половина
действительно пропадала молча. Теперь одинокое первое поле склеивается со следующей
строкой, имя тома на месте, а строка, которую разобрать не вышло, печатается как
`NOT CHECKED`.

### AC-28 — слушатели на IPv6 пропадают из снимка

Инструмент: `ssh_snapshot` · Стенд: подтверждено по коду · Серьёзность: мелочь
Код: `src/tools/snapshot-tool.ts:270-280`

Порт вырезается из локального адреса через `cut -d: -f2`. Для IPv4 (`0.0.0.0:443`) это
работает, для IPv6 (`[::]:4847`) второе поле пусто, запись отсеивается фильтром
`!isNaN(parseInt(port))`.

На доступных стендах живьём не воспроизводится: там каждый IPv6-слушатель дублируется на
IPv4, и порт всё равно попадает в список с другой строки.

**Исправлено, воспроизведено стендом.** На alpine поднят второй sshd, слушающий только
`:::4847`: прежний конвейер отдавал на нём пустую строку, снимок показывал один порт 22.
Теперь порт берётся после последнего двоеточия, и в списке рядом с 22 стоит 4847;
совпадающие порты IPv4 и IPv6 печатаются одной строкой. Стенд убран.

### AC-29 — отказ локального переименования отдаёт исключение Node

Инструмент: `ssh_download` · Стенд: все · Серьёзность: мелочь
Код: `src/managers/local-path-ops.ts:56-58`

`fs.rename` вызывается без обёртки: при нехватке прав на локальный каталог или занятом
файле наружу уходит сырой `EACCES`/`EPERM` вместе с внутренним временным именем
`.upload-<hex>.<имя>`. Это уже после того, как файл скачан — то есть данные на месте, а
сообщение выглядит как поломка.

### AC-31 — «хук обновления не настроен» без права его прочитать

Инструмент: `ssh_tls_check` · Стенд: подтверждено по коду · Серьёзность: важно
Код: `src/tools/audit-tool.ts:549-552`, `591-593`, схема — `104-118`

Наличие deploy-хука Let's Encrypt проверяется чтением `/etc/letsencrypt/…` без sudo, а
параметра `sudo` у инструмента нет вовсе. Под непривилегированным пользователем каталог
недоступен, ошибки погашены через `2>/dev/null`, и отчёт печатает
`WARNING: no Let's Encrypt deploy_hook configured` — как установленный факт, хотя проверка
не состоялась. На реальном сервере под root предупреждение выводится и означает ровно то,
что написано, — различить эти два случая по ответу нельзя.

**Исправлено.** Команда различает три состояния каталога, у инструмента появился параметр
`sudo`, и ответы теперь разные:

| Что на сервере | Ответ |
|---|---|
| каталог есть, читать нечем | `UNKNOWN: Let's Encrypt renewal config not readable — retry with sudo: true` |
| Let's Encrypt не установлен | `INFO: Let's Encrypt is not set up on this server` |
| установлен, хука нет | `WARNING: no Let's Encrypt deploy_hook configured` |
| хук настроен | ни одного флага |

Замерено на debian с каталогом `/etc/letsencrypt/renewal` под `700`: профиль `deploy` без
`sudo` — `UNKNOWN`, он же с `sudo: true` — `WARNING`; alpine без Let's Encrypt — `INFO`.

## Не дефект, но неудобно

- **Объём одного ответа.** Буфер транспорта — 10 MiB, и весь он уходит в ответ MCP одним
  куском: кейс A30 вернул 10 485 851 знак (пометка об обрезке на месте и текст верный).
  Для клиента с ограниченным контекстом это много; порог задумывался как защита транспорта,
  а не как разумный размер ответа.

## Расхождения с документацией (вход для CORE_12)

- `ssh_file_write` принимает `sudo`, `verify`, `atomic`, `mode`, `binary` **внутри объекта
  файла** (`files`), а не параметрами вызова. Глобальная инструкция пользователя описывает
  их как параметры вызова: `ssh_file_write({ verify: true, atomic: true })` — такой вызов
  схему не пройдёт. Проверить формулировки в README.
- `atomic` в схеме помечен как игнорируемый («принимается, чтобы старые вызовы работали») —
  README не должен обещать им управление.

## Что проверено и держится

Группа A, `ssh_exec` (30 вызовов, три контейнера и реальный сервер):

- вывод, код возврата, разделение stdout и stderr; несуществующая команда — код 127 назван;
- `sudo` под непривилегированным пользователем на BusyBox и coreutils;
- вход по паролю (askpass) без ключа;
- `cwd`, включая внятную ошибку на несуществующем каталоге;
- кавычки, `$(…)`, `*`, перевод строки внутри команды — как в обычном shell;
- dropbear-устройство отвечает наравне с остальными;
- обрезка вывода на 10 MiB с явной пометкой;
- guard на удаление: корень, `/*`, системный каталог, домашний каталог и **симлинк на
  системный каталог** — блокируются с указанием причины и способа подтвердить; обычное
  удаление внутри песочницы не задето. Корень и `/etc` на обоих контейнерах после серии
  попыток целы.

Группа B, файловые инструменты (33 вызова):

- запись и чтение текста с кириллицей; несколько файлов одним вызовом с отчётом по каждому;
- `mode` доезжает до файла (проверено `stat`: 600), запись под `sudo` даёт `root:root 644`;
- двоичная запись из base64 — байты совпадают побайтно (`00 01 02 03 ff fe fd 00`, 8 байт);
- отказ на чтении файла крупнее буфера — с советом взять `ssh_download` или читать
  диапазонами, вместо молчаливого огрызка;
- внятные отказы: нет файла, каталог вместо файла, нет каталога для списка, нет прав;
- имена с пробелом, `*`, тильдой и обратным слэшем — читаются и попадают в список; шаблон
  `*.txt` отбирает ровно `.txt`, включая злые имена, и не тянет `.bin`;
- рекурсивный список показывает вложенный каталог;
- BusyBox: запись со сверкой и чтение имени с пробелом; dropbear-устройство пишет файлы;
- реальный сервер: запись со сверкой и список песочницы.

Группа C, передача (47 вызовов, включая безопасность):

- отправка и скачивание файла, двоичного 1 МБ и крупного 20 МБ — хеш на сервере совпадает
  с локальным во всех случаях; скачанное сверено локально побайтно;
- каталог с вложенностью в обе стороны, включая имя с пробелом внутри дерева;
- **сверка в передаче сообщается явно** — `sha256: … (verified)`, в отличие от
  `ssh_file_write` (см. AC-04);
- злые имена: пробел, `*`, тильда, обратный слэш, перевод строки — уезжают под своими
  именами, в домашнем каталоге ничего лишнего не появляется;
- `~/путь` как назначение раскрывается в `/root/…`; каталога с именем `~` не создаётся;
- `sudo` + `mode` + `owner` вместе дают `root:root 640`;
- `overwrite: false` отказывает на существующем файле;
- `recursive` — флаг «форсировать», по умолчанию тип определяется по stat; на файле с
  `recursive: true` — внятный отказ;
- BusyBox и dropbear-устройство без sftp: файл и каталог передаются, хеши сходятся;
- скачивание отсутствующего файла и файла без прав — отказ, локально ничего не создано;
- **инъекции отбиты**: `mode: "644; touch …"` и `owner: "root:root; touch …"` отклонены

  выполнилась;
- **сохранность при отказе**: неудачный `chown` не оставляет ни файла назначения, ни
  временного следа, а прежнее содержимое файла на месте (проверено хешем).
