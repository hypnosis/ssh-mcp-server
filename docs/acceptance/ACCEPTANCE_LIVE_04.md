# Приёмка 04 — свежий сервер под ключ

Четвёртый заход. Отличие от прошлых: инструментами MCP выполнялась не проверка, а работа —
поднятие доступа к новой машине, аудит безопасности и закрытие найденного, включая
перезагрузку. Сценарий, где ошибка инструмента стоила бы доступа к серверу.

**Итог: работа сделана целиком, новых дефектов два — TD-18 и TD-19.** Красные флаги аудита
с двух критичных до нуля. Следом на той же машине прошла боевая раскатка VPN-узла — там
инструменты работали уже не по нашему сценарию, а по чужому, и новых дефектов не дали.

## Обстановка

| Что | Значение |
|---|---|
| Машина | `finlab` — AdminVPS, Ubuntu 24.04, KVM, свежая, без нагрузки |
| Сервер MCP | `ssh_live` → `.claude/worktrees/core11/dist/index.js` |
| Дата | 2026-08-15 |

Особенность площадки: провайдер режет **входящий** 22 (в его базе знаний 22 назван только
исходящим). Первый вход возможен лишь через noVNC-консоль панели, а её вставка теряет Shift
на не-буквенных клавишах — `&&` приезжает как `77`, `>` как `.`, `|` как `\`. Команды для
консоли пришлось собирать из букв, цифр и `/ . - ; ' =`, а публичный ключ передавать не
вставкой, а `ssh-copy-id` с мака.

## Что делалось инструментами

| Шаг | Инструмент | Результат |
|---|---|---|
| Снятие baseline | `ssh_audit_baseline` | две критичные находки, две предупредительные |
| Поиск следов взлома | `ssh_log_search` | 5337 неудачных входов, честная пометка об обрезке выдачи |
| Разбор упавшего юнита | `ssh_service_status` | причина названа прямо: `ipv4: Address already assigned` |
| Запись конфигурации sshd | `ssh_file_write` | sha256 сверен |
| Правки и проверки | `ssh_exec` пакетами | порядок команд сохранён, коды возврата честные |
| Обновление 170 пакетов | `ssh_exec` + `detach` | задача пережила разрыв, `ssh_job_status` следил |
| Перезагрузка и возврат | `ssh_exec` | машина вернулась на новом ядре, вход по ключу цел |

## Находки

### TD-18 — красный флаг называет порт, которого никто не слушает

`ssh_audit_baseline` выдал `"PasswordAuthentication yes on port 22"`, тогда как в его же
секции `listeners` стоял `0.0.0.0:4847`. Порт берётся из `sshd -T`, а на Ubuntu 22.04+ его
задаёт `ssh.socket`. Разбор и план — [tech-debt/archive/audit-port-mismatch_18.md](../tech-debt/archive/audit-port-mismatch_18.md).

**Закрыто** спринтом FIX_16: флаг паролей больше не зависит от порта, а порт из
конфигурации сверяется со слушателями — расхождение стало отдельным предупреждением.

### Ложное срабатывание сторожа разрушительных команд

На команду `test -f /var/run/reboot-required && cat /var/run/reboot-required` сторож
напечатал `⚠️ DANGEROUS COMMAND: reboot detected`. Слово `reboot` встретилось в **имени
читаемого файла**, ничего не выполнялось и не перезагружалось. Команда прошла — это
предупреждение, а не отказ, — но сигнал шумит ровно там, где его будут читать чаще всего:
`/var/run/reboot-required` проверяется в любом аудите, в том числе нашим же
`ssh_audit_baseline`. Разбор и план — [tech-debt/archive/pattern-warnings-match-substring_19.md](../tech-debt/archive/pattern-warnings-match-substring_19.md).

**Закрыто** спринтом FIX_16: проверяется имя в позиции команды, а не слово в строке.

### Профиль подхватывается на лету

Новый профиль, дописанный в файл профилей во время работы, был виден работающему серверу
MCP с первого вызова — перезапуск не потребовался. Проверено сразу после добавления
`finlab`.

### Замер порта снаружи врёт при `</dev/null`

Не дефект инструментов, а ошибка метода, стоившая двух неверных заявлений: `nc host port
</dev/null` закрывает соединение по EOF раньше, чем приходит баннер SSH, и порт объявляется
закрытым при живом демоне. Надёжно — `nc -d` либо TCP-коннект с другой машины. Тот же класс,
что пустой `grep` из §9 правил проекта.

### Аудит молчал про фаервол

Найдено при разборе кода после приёмки, а не по сигналу: раздел `firewall` собирался и
печатался, но в классификации не участвовал ни одной строкой. Машина с выключенным
экраном получала пустой список замечаний — именно так выглядел свежий сервер, и дыру
тогда нашли глазами.

Там же — второе: смотрелась только таблица `filter`. Docker публикует порты правилами в
`nat`, и они срабатывают раньше правил ufw; отчёт при этом честно печатал «экран включён».

**Закрыто** спринтом FIX_16, задачи 3 и 4. Проверено на finlab поднятым контейнером с
опубликованными портами:

```
WARNING:
  - docker publishes port(s) 19999, 19998 past the firewall (nat/DOCKER runs before the filter rules)
  ok: firewall active (ufw)
```

## Аудит и что закрыто

| Было | Стало |
|---|---|
| вход по паролю разрешён, root по паролю разрешён, 5337 попыток подбора за 31 час | `PasswordAuthentication no`, `PermitRootLogin prohibit-password` |
| порт держал `ssh.socket`, в конфигурации значился 22 | `ssh.service`, единственный порт 4847, сокет отключён |
| фаервола нет: `ufw` выключен, политика `ACCEPT`, ноль правил | `ufw` активен, входящее запрещено, открыт только 4847 |
| в группе `sudo` числился несуществующий пользователь провайдера | группа пуста, `adm` оставлен только `syslog` |
| два юнита в `failed`: `ifupdown` дрался с `systemd-networkd` | `failed` пуст, сеть держит `systemd-networkd` |
| работало ядро 6.8.0-36 при установленном 6.8.0-137, 170 обновлений | ядро 6.8.0-137, осталось 3 отложенных обновления |

Попыток подбора после смены порта — ноль; последняя запись в журнале датирована минутой
до переноса SSH.

`fail2ban` не ставился и не предлагался: при входе только по ключу защищать нечего, а
запирать агента он умеет.

## Боевая раскатка: инструменты в чужом сценарии

После аудита на той же машине разворачивался VPN-узел. Задачи ставил другой агент, план и
код ролей были его, а исполнение и проверка — наши. Ценность этой части в том, что сценарий
писали не мы: подтвердить свои же ожидания легко, а здесь инструменты попали в чужой порядок
действий.

**Важная оговорка, без которой отчёт был бы неправдой.** Раскатку вела `ansible` своим
транспортом, не нашим. Инструменты MCP занимались другим: замерами до и после, диагностикой
падений, приёмкой результата. Испытание прошла не доставка файлов, а работа с сервером в
режиме расследования.

| Прогон | Итог | Наша роль |
|---|---|---|
| `node` — конфиги xray и nginx, два контейнера | ok=32, changed=13 | приёмка портов, монтирований, ufw |
| `sub` — выдача подписок по токену | упал | поиск причины |
| `sub` повторно | ok=13 | замер кодов ответа |
| `firewall_open` — 443 наружу | ok=5, changed=1 | проба снаружи, проверка целости SSH |
| `node` повторно — новые витрины | ok=33, changed=3 | проба четырёх адресов снаружи |

### Разбор чужого падения

Роль `sub` упала на своей же проверке: верный токен вернул 404. Причину нашли пакетными
вызовами `ssh_exec` — сравнением того, что видит хост, с тем, что видит контейнер:

```
docker exec nginx ls -d /opt/nginx/html/sub
ls: /opt/nginx/html/sub: No such file or directory
```

В `map` стоял путь хостовой файловой системы, а `alias` резолвится внутри контейнера, где
каталог смонтирован под другим именем. Каталог `/opt` внутри существует, поэтому nginx не
ругался на конфигурацию — он честно отвечал 404 на живой путь в никуда.

Диагностика по логам была закрыта с двух сторон: в конфиге `access_log off` и
`error_log /dev/null`, а `docker logs` на этой машине отвечает
`configured logging driver does not support reading`. Причина нашлась сравнением, а не
чтением журналов.

### Чего инструменты не искажали

Через `ssh_exec` в боевом порядке уехали и вернулись целыми:

- Go-шаблоны `docker inspect` с `{{range}}`, `{{end}}` и `\n` внутри;
- `sed -E` с классами символов и квантификаторами — им маскировались токены **на сервере**,
  чтобы секреты не попадали ни в наш ответ, ни в чат;
- многострочный скрипт с `$(...)`, вложенными кавычками и перенаправлениями;
- `sudo` в параметрах вызова, не в тексте команды.

Это то самое семейство из §5 правил проекта, на котором смена транспорта ловилась весь
прошлый спринт. В чужом сценарии оно отработало без единого искажения.

### Что показали замеры сверх задания

Три проверки добавлены не для отчётности — без них зелёный результат ничего бы не значил:

| Замер | Зачем |
|---|---|
| выдуманный 32-значный токен → 404 | верный токен тоже давал 404, пока путь был сломан; пара 200/404 отличает отбор по списку от общего отказа |
| первые байты тела подписки → `dmxlc3M6` | это `vless:` в base64: отдаётся подписка, а не пустой файл с кодом 200 |
| несуществующий путь витрины → 404 | иначе четыре ответа 200 не отличить от сервера, отдающего одну страницу на что угодно |

Порт снаружи мерили живым HTTPS-ответом и добавляли заведомо закрытый порт для контроля:
у машины, с которой шла проверка, бывает ложный SYN-ACK, и «открыт» выглядит любой порт.
Тот же класс ошибки, что и `nc </dev/null` выше.

### Где ошиблись мы, а не инструменты

- `--resolve` вместе со значением ушёл в локальный `curl` одним аргументом — своя ошибка
  цитирования в оболочке, инструменты ни при чём.
- В одном прогоне хост назвался `s4` вместо `finlab`. Разбор результатов остановлен до
  выяснения: алиас в инвентаре переименован, адрес прежний. Минута проверки против записи
  на чужую машину — в том числе на ту, которую разрешено только читать.

Новых дефектов инструментов эта часть не дала.
