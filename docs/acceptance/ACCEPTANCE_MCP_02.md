# Приёмка 02 — сборка под живым MCP-клиентом

Второй заход приёмки ветки `feat/openssh-transport`. Отличие от первого
(`ACCEPTANCE_BUGS.md`): там инструменты звал самописный harness, здесь — настоящий клиент
Claude Code через подключённый MCP-сервер. То есть проверяется ровно тот путь, которым
пойдёт пользователь пакета.

Порядок: сначала то, чего в первом заходе не было вовсе (фоновые задания, `detach`,
структурированный ответ, отмена), затем регрессия по закрытым находкам AC-01…AC-31.

Находки не чиним — фиксируем и разбираем причину.

**Итог: блокеров нет.** Четырнадцать находок — семь важных и семь мелочей.

Первый заход закрыт хорошо: шестнадцать его находок, включая оба блокера (AC-10, AC-18),
подтверждены живым вызовом как исправленные. AC-11 проверить было нечем — он с боевого
сервера. Ещё две закрыты наполовину: остатки AC-13 и AC-06 записаны здесь как MCP-09 и
MCP-10.

Порядка восьмидесяти вызовов: основная часть через клиент Claude Code, десяток — напрямую
по stdio, где клиент мешает замеру (объём ответа, признак ошибки, отмена, сторож удаления).
Скрипты замеров лежат в scratchpad и в репозиторий не идут. Следы прогона со стендов убраны:
`/tmp/acc2`, каталоги задач и оставшиеся процессы сняты, проверено списком.

Важные находки делятся на два почерка, и оба — не про новый код, а про то, как он писался:

1. **Приём применён не ко всем однотипным местам.** Маркеры «утилиты нет» стоят у
   межсетевого экрана, но не у служб и обновлений (MCP-06). Проверка «нет такой задачи»
   есть у состояния, но не у вывода и снятия (MCP-01, MCP-02). Признак ошибки выставляется
   у одиночных вызовов, но не у пакетных (MCP-13), и не у отказа сторожа удаления (MCP-12).
   Это §4 CLAUDE.md дословно: где в коде пара, сторож поставлен на первый элемент.
2. **Склейка команды строкой.** `cd <каталог> && <команда>` защищает только первую часть
   строки (MCP-04) — ровно тот класс, о котором §5: сменили слой, разбирающий данные, и
   поймали семейство, а не один случай.

Ни одна из важных не нашлась бы юнитами: часть требует сервера, где systemd не отвечает,
часть — сервера, где не удаётся `cd`, часть — чтения признака ответа на уровне протокола.
Это правило №1 CLAUDE.md в очередной раз: инструментами оно не заменяется.

## Находки

### MCP-01 — вывод несуществующей задачи выглядит как пустой вывод существующей

Задача была запущена на `mcp-debian`, а вывод запрошен с профилем `mcp-alpine` — обычная
описка, когда стендов несколько.

```
ssh_job_output { profile: "mcp-alpine", id: "msu8swkv-0cc4fe25" }
→ Job msu8swkv-0cc4fe25 output: 0 bytes total, read 0 from offset 0.
  Next offset: 0
  (no output at this offset)
```

То же самое на выдуманном идентификаторе (`totally-absent-job`) и на том же профиле, где
задача заведомо не заводилась. Ответ не отличается ничем.

Ожидалось: «нет такой задачи» — ровно так отвечает соседний инструмент.

```
ssh_job_status { profile: "mcp-debian", id: "no-such-job-12345678" }
→ Job no-such-job-12345678: no such job on the server (it may have been cleaned up)
```

**Причина.** Отсутствие каталога задачи проверяет только команда состояния:
`src/utils/job-command.ts:162` — `if [ ! -d "$d" ]` печатает `state=missing`, и
`handleStatus` разворачивает это в честный ответ. Команда вывода
(`src/utils/job-command.ts:186`) проверяет другое — наличие файла `output.log` — и на его
отсутствие печатает `size=0`. Дальше `handleOutput` (`src/tools/job-tools.ts:223`) видит
пустой текст и пишет «(no output at this offset)». Каталога нет, файла нет, задачи нет —
на выходе «задача есть, вывода пока нет».

Это нарушение инварианта «честный ответ» (CLAUDE.md §7): «проверить нечем» подан как
«ничего нет». Тот же класс, что AC-12 первого захода, только там пустыми выглядели службы
и порты в снимке.

Форма дефекта — из §4: три команды семейства (`status`, `output`, `kill`) строятся рядом,
различать отсутствие научили одну.

**Перепрогон 2026-08-15 после FIX_15: не воспроизводится.** Чужой идентификатор с профиля
`mcp-alpine` и выдуманный `totally-absent-job` дают один ответ — `Job …: no such job on the
server (it may have been cleaned up)`.

### MCP-02 — снятие несуществующей задачи объясняется несуществующей причиной

```
ssh_job_kill { profile: "mcp-alpine", id: "msu8swkv-0cc4fe25" }
→ Job msu8swkv-0cc4fe25 never recorded a pid — there is nothing to signal.
```

Задачи на этом стенде нет вовсе. Сообщение же описывает другой случай: задача есть, но не
успела записать pid. Пользователь читает его как «задача завелась криво».

**Причина.** `src/utils/job-command.ts:206`: `pid=$(cat "$d/pid" 2>/dev/null)` при
отсутствующем каталоге возвращает пустую строку, и ветка `reason=nopid` срабатывает на два
разных случая. Отдельного `missing`, как в команде состояния, здесь нет —
`src/tools/job-tools.ts:283` печатает то, что ему передали.

Для сравнения, на реально снятой задаче ответ верный: `Job … is already gone — nothing to
stop.`

**Перепрогон 2026-08-15 после FIX_15: не воспроизводится.** Снятие задачи с чужого стенда
отвечает `no such job on the server`; про «не записан pid» речь заходит только там, где
каталог задачи действительно есть.

### MCP-03 — по списку задач не понять, что в них запущено

```
ssh_job_list { profile: "mcp-debian" }
→ 1 background job(s):
    msu8swkv-0cc4fe25  running  2026-08-15T10:38:06.000Z (unix 1786790286), 119 bytes
```

Каталог задачи хранит её команду в файле `cmd` (`src/utils/job-command.ts:143`), и
`ssh_job_status` её показывает — читает отдельным маркером (строка 170). Команда списка
(`src/utils/job-command.ts:227-239`) этот файл не открывает вовсе, поэтому и печатать
нечего. Пользователь, вернувшийся к серверу через день, видит набор идентификаторов и не
знает, какой из них что делает: чтобы понять, нужен вызов состояния на каждый.

Скорее доработка, чем дефект. Отдавать команду целиком в строку списка нельзя — она бывает
многострочной; напрашивается первая строка с обрезкой по длине.

### MCP-04 — команда выполняется не в том каталоге и рапортует успех

Каталог задан несуществующий, команда — из нескольких частей через `;`.

Фоновая задача:

```
ssh_exec { profile: "mcp-debian", cwd: "/nonexistent-dir-xyz", detach: true,
           command: 'echo "before"; pwd; echo "after"' }
→ Command: cd '/nonexistent-dir-xyz' && echo "before"; pwd; echo "after"

ssh_job_status → finished, Exit code: 0
ssh_job_output →
  sh: 1: cd: can't cd to /nonexistent-dir-xyz
  /root
  after
```

Задача отчиталась кодом 0. При этом `echo "before"` не выполнилась (её съел `&&`), а `pwd`
и `echo "after"` выполнились — в `/root`, то есть в каталоге, которого никто не просил.

Обычный вызов ведёт себя так же:

```
ssh_exec { profile: "mcp-debian", cwd: "/nonexistent-dir-xyz",
           command: 'pwd; echo "worked anyway"' }
→ worked anyway
  STDERR: bash: line 1: cd: /nonexistent-dir-xyz: No such file or directory
```

А вот через массив команд поведение правильное — ничего не выполнено, код 2 на каждой:

```
ssh_exec { profile: "mcp-alpine", cwd: "/nonexistent-dir-xyz",
           command: ["pwd", "touch marker-should-not-exist"] }
→ [1/2] STDERR: sh: cd: line 0: can't cd to /nonexistent-dir-xyz …  Exit code: 2
  [2/2] STDERR: sh: cd: line 0: can't cd to /nonexistent-dir-xyz …  Exit code: 2
```

**Причина.** `cwd` подставляется склейкой `cd <каталог> && <вся строка команды>`:
`src/managers/ssh-executor.ts:98` для обычного вызова и `src/tools/exec-tool.ts:347` для
фоновой задачи. `&&` связывает только ближайшую команду, поэтому всё, что идёт после `;`,
`&&` не касается — оно выполнится независимо от того, удался переход или нет. В режиме
массива каждая команда уходит отдельным вызовом исполнителя и получает собственный `cd …
&&`, поэтому там дыры нет: то же самое место кода, но текст команды состоит из одной части.

Отсюда и код возврата: задача заканчивается последней командой строки, у неё код 0, и
`exit_code` записывается нулём — успех.

Чем это плохо на практике: `cwd: "/opt/app"` с опечаткой и командой вида
`rm -rf ./cache; systemctl restart app` выполнит удаление в домашнем каталоге и назовёт это
успехом. Инвариант «неполный ответ не выдаётся за полный» (CLAUDE.md §7) нарушен на самом
опасном участке — там, где команда меняет файлы.

Лечится тем же приёмом, каким уже пользуется `sudo` строкой выше по коду
(`ssh-executor.ts:93`): завернуть команду целиком — `cd <каталог> && sh -c <команда>`, тогда
`;` останется внутри обёртки. Для фоновой задачи — то же самое в `exec-tool.ts:347`.

**Перепрогон 2026-08-15 после FIX_15: не воспроизводится.** Связка стала
`cd <каталог> || exit 1; <команда>` (обёртку выбрал замер: команда на `&` внутри `{ … ; }` —
синтаксическая ошибка на BusyBox и dropbear). Обычный вызов и фоновая задача при неудачном
переходе не выполняют ничего и заканчиваются кодом 1, массив не создал
`marker-should-not-exist`.

### MCP-05 — чтение вывода задачи ничем не ограничено

Задача напечатала 20 000 строк (848 890 байт). Одно чтение вернуло их целиком:

```
ssh_job_output { profile: "mcp-debian", id: "msu9106a-6573a167", offset: 0 }
→ ответ 848 988 байт, 20 004 строки
```

Замерено вне клиента (`scratchpad/probe-size.mjs`), чтобы не топить контекст сессии. В
самом Claude Code такой ответ клиент перехватывает и складывает во временный файл — то есть
последствие мягче, но вывод из диалога всё равно исчезает, а токены на пересылку уже
потрачены.

Попросить кусок нечем: у инструмента есть `offset`, но нет ни `limit`, ни `maxBytes`.
Единственный потолок — общий предел транспорта в 10 МБ
(`src/utils/output-notes.ts:11`), то есть ответ может быть на порядок больше замеренного.

Это ровно AC-09 первого захода (`ssh_log_search` отдал 3736 строк одним ответом), только в
инструменте, которого тогда ещё не было: урок в новый код не переехал.

Рядом два наблюдения о курсоре:

- `offset: 900000` при размере 848 890 отвечает честно — «read 0» — но `Next offset`
  остаётся 900 000. Если задача продолжит писать, следующее чтение с этой позиции
  перепрыгнет через байты 848 890…900 000 и потеряет их молча.
- `offset: -50` не отвергается, а тихо превращается в 0
  (`src/tools/job-tools.ts:201`, `Math.max(0, …)`) — и вместо ожидаемого «последние 50 байт»
  или отказа возвращается весь файл. Отрицательное смещение — это ошибка ввода, а остальные
  инструменты такие отвергают.

### MCP-06 — «нечем проверить» снова подано как «ничего нет»

Стенд `mcp-alpine`: ни `systemctl`, ни `apt`, ни `docker`, ни `ufw`, ни `iptables`
(проверено `command -v` по каждому). Ответ аудита:

```
ssh_audit_baseline { profile: "mcp-alpine", include: ["services","docker","firewall","updates"] }
→ {"unavailable":[],
   "services":{"failed":[],"running_count":0},
   "firewall":{"ufw":{"status":"not_installed"},"iptables":{"status":"not_installed"}},
   "updates":{"upgradable":0,"reboot_required":false},
   "docker":null}
```

Стенд `mcp-debian`: `systemctl` установлен, но systemd не является init внутри контейнера.
Проверено напрямую:

```
systemctl list-units --type=service --state=running
→ System has not been booted with systemd as init system (PID 1). Can't operate.
  Failed to connect to bus: Host is down
```

Аудит при этом снова отвечает `"services":{"failed":[],"running_count":0}` и
`"unavailable":[]`.

То есть «служб ноль» и «обновлений ноль» — утверждения о сервере, которых никто не
проверял. Раздел `unavailable`, заведённый ровно для таких случаев, остаётся пустым. Про
межсетевой экран и docker ответ, наоборот, честный: `not_installed` и `null`.

**Причина.** Разделы собираются одной пачкой команд, и маркер «утилиты нет» проставлен
только у части:

- `src/tools/audit-tool.ts:222-235` — у `firewall` есть `NO_UFW` / `NO_IPTABLES`, и в
  комментарии на 220-221 прямо описан этот же урок: «без маркеров отсутствие ufw и отказ по
  правам дают тот же пустой вывод, что и выключенный экран».
- `src/tools/audit-tool.ts:212-213` — у `services` маркера нет:
  `systemctl … 2>/dev/null | wc -l`. Нет systemctl, не поднят systemd, отказано по правам —
  во всех трёх случаях пустой вывод, `wc -l` даёт 0, и `audit-tool.ts:336` кладёт этот ноль
  в `running_count`.
- `src/tools/audit-tool.ts:238` — у `updates` маркера нет:
  `(apt list --upgradable 2>/dev/null | … | wc -l) || echo 0`. На системе без apt получается
  тот же ноль, и `audit-tool.ts:353` записывает его как факт.

Приём известен, работает и применён — но к одному разделу из трёх. Это форма §4 CLAUDE.md:
где в коде однотипная пара (тройка), сторож поставлен на первый элемент.

AC-14 первого захода при этом закрыт честно и повторно проверен: `include: ["system",
"mem", "ssh"]` возвращает ровно три раздела, невыбранных полей в ответе нет. Здесь другой
вход в тот же класс — раздел запрошен, но выполнить его нечем.

**Перепрогон 2026-08-15 после FIX_15: не воспроизводится.** На `mcp-alpine` —
`unavailable: ["services (no systemctl on the server)", "updates (no apt on the server)"]`,
разделов `services` и `updates` в ответе нет. На `mcp-debian` в `unavailable` ушли только
службы («systemd did not answer»), а `updates: {upgradable: 0}` остался — там apt рабочий, и
этот ноль честный.

### MCP-07 — снимок объявляет, что активных служб нет, не сумев их спросить

Стенд `mcp-debian`: `systemctl` установлен, но systemd внутри контейнера не init, и любая
команда к нему отвечает «System has not been booted with systemd as init system (PID 1).
Can't operate».

```
ssh_snapshot { profile: "mcp-debian" }
→ SERVICES
    No active services detected
```

На `mcp-alpine` и `mcp-router`, где `systemctl` нет вовсе, ответ честный: «NOT CHECKED: no
systemctl on the server». То есть механизм признания в снимке есть — он просто отвечает на
другой вопрос.

**Причина.** `src/tools/snapshot-tool.ts:202-206` проверяет наличие двоичного файла:
`command -v systemctl >/dev/null && echo yes || echo no`. Есть файл — значит «проверка
доступна». Дальше `systemctl is-active <служба>` (строка 211) на неработающем systemd
отвечает не результатом, а отказом, и подстановка `|| echo inactive` превращает отказ в
«служба не запущена». Все службы оказываются `inactive`, и печать сводит это к «No active
services detected» (`snapshot-tool.ts:503`).

Тот же класс, что MCP-06, но в другом инструменте и на другой развилке: там не проверяли
наличие утилиты, здесь проверяют наличие, но не работоспособность.

**Перепрогон 2026-08-15 после FIX_15: не воспроизводится.** `mcp-debian` — `NOT CHECKED:
systemd did not answer on this server`; `mcp-alpine` и `mcp-router` — прежнее `NOT CHECKED:
no systemctl on the server`, слово в слово. Случай «шина отвечает» живьём не проверен: стенда
с работающим systemd в лаборатории нет, он закрыт юнитом на записанном ответе.

### MCP-08 — на BusyBox снимок не показывает аптайм

```
ssh_snapshot { profile: "mcp-alpine" }  → Uptime: unknown
ssh_snapshot { profile: "mcp-router" }  → Uptime: unknown
ssh_snapshot { profile: "mcp-debian" }  → Uptime: 2 days, 9 hours, 58 minutes
```

При этом аптайм на стенде доступен двумя способами:

```
uptime          → 10:53:55 up 2 days, 9:58, 0 users, load average: 1.13 …
cat /proc/uptime → 208686.52 3747074.63
```

**Причина.** `src/tools/snapshot-tool.ts:187` читает `uptime -p` с запасным ответом
`unknown`. Длинных и «человекочитаемых» опций у BusyBox нет — это записано в CLAUDE.md §3
как известное расхождение стендов. Запасной путь через `/proc/uptime`, который есть на всех
трёх стендах, не предусмотрен.

### MCP-10 — в ошибке записи видно, как инструмент устроен внутри

```
ssh_file_write { profile: "mcp-debian-deploy", files: { path: "/etc/acceptance-denied.txt", … } }
→ Error: Command failed (exit 1): cat > '/etc/acceptance-denied.txt (staging copy)' —
  bash: line 1: /etc/acceptance-denied.txt: Permission denied
```

Пользователю достаточно «нет прав на запись `/etc/acceptance-denied.txt`». Вместо этого он
видит команду оболочки, номер строки в ней и пояснение «(staging copy)» внутри кавычек —
так, будто это часть имени файла.

### MCP-12 — заблокированный снос отвечает как успешный вызов

Сам сторож работает безупречно. Проверено тремя формами на `mcp-alpine` (цель — пустой
`/home`, чтобы промах сторожа ничего не стоил):

```
rm -rf /home        → ⛔ BLOCKED: "/home" is a system directory. The command was NOT executed.
T=/home; rm -rf $T  → ⛔ BLOCKED: "$T" is expanded by the server … cannot be checked before the command runs.
rm -rf /ho*         → ⛔ BLOCKED: "/ho*" is expanded by the server …
```

В пачке команд отвергается весь вызов целиком: `["echo first-ran", "rm -rf /home", "echo
third-ran"]` не выполнил ни одной — ни до, ни после опасной. Это правильно и так и
задумано (`src/tools/exec-tool.ts:191-193`).

Не в порядке одно: **у этого ответа нет пометки ошибки**. Замер полей ответа:

| Вызов | `isError` |
|---|---|
| таймаут | `true` |
| чтение несуществующего файла | `true` |
| неизвестный профиль | `true` |
| **блокировка сноса системного каталога** | **отсутствует** |

То есть самый ответственный отказ во всём наборе — единственный, который приходит как
обычный удачный ответ с текстом.

**Причина.** `src/tools/exec-tool.ts:195-197`: отказ возвращается как
`{ content: [{ type: 'text', text: refusal }] }`, без `isError: true`. Остальные отказы
идут через общий путь ошибок и пометку получают.

Чем это плохо: клиент или агент, который смотрит на признак ошибки, а не читает текст,
сочтёт снос выполненным и пойдёт дальше — например, отчитается «каталог очищен» и начнёт
разворачивать на его место новое. AC-03 первого захода закрыт именно для того, чтобы такого
не было; здесь остался один непокрытый выход.

Отдельное наблюдение о самой проверке: в Claude Code до сервера такие команды вообще не
доходят — их режет классификатор клиента. Наш сторож в этой связке второй рубеж, и увидеть
его работу можно только вызовом в обход клиента.

**Перепрогон 2026-08-15 после FIX_15: не воспроизводится.** `rm -rf /home` на `mcp-alpine`
приходит с `isError: true`; текст отказа не изменился ни на байт (158 байт, те же три
строки с маркером `# CONFIRMED-DESTRUCTIVE`).

### MCP-13 — пакетный вызов не признаёт полный провал провалом

Один и тот же несуществующий файл, разница только в форме вызова:

```
ssh_file_read { path: "/no/such/file.txt" }                     → isError: true
ssh_file_read { path: ["/tmp/acc2/missing1.txt",
                       "/tmp/acc2/missing2.txt"] }              → isError отсутствует,
                                                                  текст начинается с «Read 2 files:»
```

То же на записи, под непривилегированным профилем:

```
ssh_file_write { files: {path: "/etc/nope3.txt", …} }           → isError: true
ssh_file_write { files: [{path:"/etc/nope1.txt"…},
                         {path:"/etc/nope2.txt"…}] }            → isError отсутствует,
                                                                  «Write 2 files:» и два ✗
```

Прочитано ноль файлов из двух, записано ноль из двух — а ответ и по форме, и по пометке
неотличим от удачного.

**Причина.** `src/tools/file-tools.ts:371` и `:467` собирают текст из накопленных исходов и
возвращают его без разбора: `return { content: [{ type: 'text', text: output }] }`.
Признак ошибки не выставляется никогда, а заголовок печатает `results.length` — сколько
файлов *обработано*, а не сколько удалось. Одиночная форма идёт другим путём — через общий
обработчик ошибок — и пометку получает.

Частичный исход (один прочитан, один нет) пометки, разумеется, и не должен иметь: там
результат действительно частичный, и он честно показан значками ✓ и ✗. Речь только о случае,
когда не удалось ничего.

Форма та же, что у MCP-12: инструмент отказал, а по признаку ответа этого не видно.

**Перепрогон 2026-08-15 после FIX_15: не воспроизводится.** Два несуществующих файла —
`isError: true` и заголовок `Read 0/2 files:`; две записи в `/etc` под непривилегированным
профилем — `isError: true`, `Write 0/2 files:`. Частичный исход пометки по-прежнему не
получает: `Write 1/2 files:` приходит без `isError`, как и задумано.

### MCP-14 — отказ в доступе назван молчанием сервера

```
ssh_monitor { action: "test", profile: "mcp-alpine-nocreds" }
→ ❌ Connection test failed: mcp-alpine-nocreds did not answer in 58ms
```

Сервер ответил, и быстро: он отказал в аутентификации. Тот же профиль через `ssh_exec`
объясняет всё точно: «Authentication failed for 127.0.0.1:2231 … Permission denied
(publickey,password,keyboard-interactive)».

«Не ответил за 58 мс» отправляет разбираться с сетью и доступностью хоста вместо ключа.

**Причина.** `src/tools/monitoring-tool.ts:183`: проверка связи опирается на `runner.ping()`,
который возвращает только `ok` и `latencyMs`, а причину неуспеха не переносит. Любой отказ —
недоступный хост, отвергнутый ключ, неверный порт — сводится к одной фразе. Пометка
`isError: true` при этом стоит (строка 185), то есть проблема только в тексте.

## Что подтвердилось живым вызовом

Не находки — проверенные обещания. Записаны, чтобы второй раз их не перепроверять.

**Фоновая задача переживает обрыв соединения.** Задача запущена на `mcp-debian`, затем
локально сняты все четыре мультиплексных соединения (`kill` по процессам `[mux]`, сокетов
в `~/.ssh/ssh-mcp/` осталось 0). Следующий `ssh_job_status` поднял соединение заново и
ответил `still running`, вывод продолжал расти. Ради этого свойства фоновые задачи и
делались.

**Задача и её потомки снимаются вместе.** Запущено `sleep 300 & … ; sleep 300` — на сервере
четыре процесса в одной группе (`pgid` совпадает у всех). После `ssh_job_kill` не осталось
ни одного. Исход назван честно: «not running and left no exit code — it was stopped by a
signal or the server restarted».

**Код возврата фоновой задачи доезжает.** `exit 7` на BusyBox → `finished, Exit code: 7`.

**Курсор чтения не перекрывается и не пропускает.** Чтения с 0 и с 49 дали
непересекающиеся куски, `Next offset` каждый раз равен прочитанному концу.

**Отказы `detach` внятные.** `detach + sudo` → «a background job has nowhere to take a
password from»; `detach` с массивом команд → «detach starts a single job, got an array of 2
commands». Оба — ошибки вызова, а не молчаливое отбрасывание параметра.

**Фоновая задача работает под паролем и на dropbear.** `mcp-alpine-pw` (вход по паролю,
askpass) и `mcp-router` (dropbear, без sftp) — задачи стартуют, вывод и код возврата
собираются.

**Отмена вызова.** Замер: во время вызова локальных клиентов `ssh` — 1, через секунду после
`notifications/cancelled` — 0, ответа на отменённый запрос сервер не шлёт. Команда на
сервере при этом продолжает работать (после отмены `sleep 45` на месте). Ровно это README и
обещает (`README.md:880`), предлагая для снимаемой работы `detach` + `ssh_job_kill`.

**Структурированный ответ.** `ssh_audit_baseline` объявляет `outputSchema` и отдаёт
`structuredContent` (16 полей на полном прогоне), клиент принимает без нареканий. Побочное
наблюдение: Claude Code показывает именно структуру, а подготовленный текстовый отчёт
(2430 байт против 1189 у структуры) в диалоге не виден вовсе. Значит вкладываться дальше
имеет смысл в схему, а не в текстовое оформление.
