# Передача: починка после приёмки

Здесь всё, что нужно новой сессии: где документы, где результаты замеров, как поднять стенд
и как воспроизвести любой из дефектов.

## Документы

| Файл | Что внутри |
|---|---|
| [ACCEPTANCE_BUGS.md](ACCEPTANCE_BUGS.md) | 31 находка с разбором, доказательством и ссылкой на кейс в логе |
| [FIX_PLAN.md](FIX_PLAN.md) | План починки по чанкам, границы релиза, что сознательно не чиним |

Каталог `.acceptance/` лежит вне git — это архив замеров, не часть пакета.

## Как воспроизвести любой дефект

```bash
npm run lab:up                      # три контейнера: alpine 2231, debian 2232, router 2233
cp .acceptance/2026-08-13/harness.mjs /tmp/acc/                  # harness приёмки
cp -r .acceptance/2026-08-13/cases /tmp/acc/
cp .acceptance/2026-08-13/profiles.example.json /tmp/acc/profiles.json
# в profiles.json подставить реальный адрес сервера и пароль лаборатории (scripts/lab-up.sh)
# в harness.mjs проверить WORKTREE — он указывает на каталог со сборкой
npm run build                       # harness запускает dist, а не исходники
node /tmp/acc/harness.mjs --list                     # схемы всех инструментов
node /tmp/acc/harness.mjs /tmp/acc/cases/group-a.json
```

Harness поднимает сервер по stdio и шлёт настоящие вызовы MCP; сырой ответ каждого кейса
уходит в `logs/<набор>.jsonl`, лог сервера — в `logs/<набор>.stderr.log`. Кейс с полем
`localShell` выполняет локальную команду между вызовами (правка профилей, остановка
контейнера).

Наборы кейсов по группам: `group-a` — `ssh_exec`, `group-b` — файлы, `group-c` — передача,
`group-d` — журналы и правила путей, `group-e2` — снимок и мониторинг, `group-f` — аудит,
`group-g` — сквозное. Отдельные наборы `snapshot-*`, `review-probe*`, `steal` — точечные
замеры блокеров.

## Что важно знать до первой правки

- **Оба блокера воспроизводятся только на холодном соединении.** Снимок первым вызовом
  вешал сервер; если перед ним сделать любой `ssh_exec`, всё работает. Замер, начатый не с
  того конца, покажет зелёное. Перед замером закрыть общее соединение:
  `ssh -o ControlPath=~/.ssh/ssh-mcp/s-%C -O exit -p <порт> root@127.0.0.1`.
- **AC-18 воспроизводится только между двумя процессами**: один поднимает соединение
  законным профилем, другой ходит по нему профилем без ключа. В пределах одного процесса
  дефект не виден.
- **AC-20 и AC-31 не воспроизводятся под root** — нужен непривилегированный профиль
  (`lab-debian-deploy`). Для AC-31 на стенде нужен ещё и сам каталог:
  `docker exec mcp-debian sh -c 'mkdir -p /etc/letsencrypt/renewal && chmod 700 …'`.
- **AC-11 виден только при разных единицах в `free -h`**: на стендах памяти поровну, и обе
  величины выходят в `Gi`. Чтобы воспроизвести, на alpine подкладывается обёртка
  `/usr/local/bin/free`, печатающая `3.8Gi` всего при `506Mi` занятых. Убрать после замера.
- Замеры на реальном сервере — только чтение и только внутри `~/ssh-mcp-acceptance`; после
  приёмки этот каталог снесён, следов не осталось.
- Docker Desktop из сессии агента не стартует — просить владельца запустить вручную.

Проект `ssh-mcp-server` — MCP-сервер, через который ассистент ходит на удалённые серверы по
SSH: выполняет команды, читает и пишет файлы, передаёт каталоги, смотрит журналы, снимает
состояние машины, делает аудит. Четырнадцать инструментов. Пакет опубликован в npm, поэтому
имена инструментов и формат профилей не ломаем.

Работаем в ветке `feat/openssh-transport`, worktree `core11`. Ветка большая: она убрала
библиотеку `ssh2` и оставила один транспорт — системный клиент `ssh` с общим соединением
(ControlMaster). Код написан и покрыт тестами, дальше по плану релиз v2.0.0.

**Что произошло перед тобой.** Прошла живая приёмка: каждый инструмент вызывали так, как его
вызовет клиент — по MCP, с настоящими аргументами, на четырёх стендах (BusyBox-контейнер,
coreutils-контейнер, контейнер с dropbear без sftp — имитация роутера, и реальный рабочий
сервер). 251 вызов. Затем три агента искали в коде родственников найденным дефектам. Итог:
31 находка, из них два блокера. Всё, что утверждали агенты, перепроверено по коду и живыми
замерами; неподтверждённое отброшено.

Приёмка нужна была потому, что юниты с моками показывали зелёное, а инструмент целиком —
схему параметров, формат ответа, текст ошибки — не проверял никто.

**Хорошая новость, которую важно не сломать.** Приёмка подтвердила, что держится крепко:
защита от `rm -rf` по системным каталогам и симлинкам; правила путей профиля, включая обход
через тильду, `..` и `sudo`; отбитые попытки подставить команду в `mode`, `owner`, имя
службы, домен и поисковый запрос; сохранность файла при отказе на полпути; побайтное
совпадение хешей при передаче, включая имена с пробелами и переводом строки; пароль не
попадает в логи. Починка не должна это задеть — в баг-репорте есть раздел «Что проверено и
держится», он служит списком того, что обязано остаться зелёным.

**Первый блокер (AC-10) — исправлен.** `ssh_snapshot` собирал десять показателей десятью
параллельными чтениями и на непрогретом соединении не отвечал никогда, унося за собой весь
сервер. Причина — взаимная блокировка шлюза первой команды и паспорта сервера: десятое
чтение идёт с `sudo`, из-за этого паспорт спрашивался обычной командой, то есть через шлюз,
а девять остальных чтений уже закрыли шлюз и внутри себя ждали тот же паспорт. Версия про
гонку двух кэшей, стоявшая здесь раньше, замером опровергнута: с одним экземпляром
транспорта зависание воспроизводится так же. Теперь паспорт берётся у транспорта, где проба
идёт мимо шлюза; снимок первым вызовом отвечает за 200–300 мс на всех трёх контейнерах.

**Второй блокер (AC-18) — исправлен.** Путь общего сокета был хэшем от адреса, порта и имени
пользователя, без ключа и пароля. Поэтому профиль без учётных данных выполнял команды от
root, если соседний процесс уже поднял соединение к тому же серверу законным профилем, и
закрывал этот канал за собой (AC-19). Теперь имя сокета считает сам проект — хэш от
назначения и отпечатка учётных данных, — и такой профиль получает отказ по аутентификации,
а чужое соединение остаётся живым. Профили с одинаковыми учётными данными соединение
по-прежнему делят.

**Третий класс — честность ответа — исправлен.** Инструменты отвечали так, будто проверили,
хотя проверка не выполнялась: аудит печатал «файрвол выключен, обновлений ноль» для
разделов, которые не запускались, и молчал о парольном входе на 22-м порту, если не смог
прочитать конфиг; снимок показывал 233% загрузки процессора при простое, «служб нет, портов
нет» там, где нет утилит, и 13316% занятой памяти при разных единицах; `ssh_file_write`
отвечал одинаково и когда хеш сошёлся, и когда сверять было нечем; `ssh_upload` рапортовал
об успехе, не применив запрошенного владельца. Теперь у каждого такого места три исхода
различимы в самом ответе. Разбор по каждой находке — в баг-репорте, сводка — в плане.

**Что делаем.** План согласован с владельцем, состав переспрашивать не нужно:
`docs/acceptance/FIX_PLAN.md` — четыре чанка, все четыре закрыты: зависание снимка, доступ
по чужому соединению, честность ответов, регресс. Мелочи и часть важных находок
сознательно ушли в долг (`docs/tech-debt/`, записи TD-12…TD-16) и в CHANGELOG отдельной
секцией; расширять этот список самовольно не надо.

Дальше по плану — мердж в `main` и выпуск v2.0.0. Правки чанков 3 и 4 на момент этой
записи не закоммичены: коммит делается по команде владельца.

**Как работаем.** По одному чанку, с паузой и докладом владельцу после каждого. Коммиты
только по его команде. Перед правкой — воспроизвести дефект замером, чтобы было с чем
сравнивать; после правки — тот же замер и живая проверка на обоих контейнерах.

**Ловушки, на которых замер покажет ложное зелёное** (подробности — в
`docs/acceptance/HANDOFF.md`):

- блокеры видны только на холодном соединении: один `ssh_exec` перед снимком — и всё
  работает;
- доступ по чужому соединению воспроизводится только между двумя процессами сервера;
- аудит SSH и проверка TLS врут только под непривилегированным профилем, под root они честны;
- Docker Desktop из сессии агента не стартует — попросить владельца запустить вручную.

**Правила проекта** (`CLAUDE.md`) действуют целиком. Главное здесь: функция считается
сделанной после живой проверки, а не после зелёных юнитов с моками; проверять на обоих
контейнерах, потому что наборы утилит расходятся молча; три исхода не смешивать —
получилось, не получилось, проверить нечем. Сторож каждой правки — повтор того кейса
приёмки, который на ней падал; мутации в этой работе не гоняем.

**Порядок разведки кода:** сначала семантический поиск, потом LSP по символам, потом grep по
точной строке, и только потом чтение файла целиком. Пустой ответ поиска сам по себе ничего
не доказывает.

**Где что лежит:** находки с доказательствами — `docs/acceptance/ACCEPTANCE_BUGS.md`; план и
границы — `docs/acceptance/FIX_PLAN.md`; стенд, harness и ловушки —
`docs/acceptance/HANDOFF.md`; архив замеров с логами и наборами кейсов —
`.acceptance/2026-08-13/`. Читай их по мере надобности, а не целиком: баг-репорт большой,
и каждая находка самодостаточна.

Починка закончена, регресс пройден. Начни с доклада владельцу о состоянии ветки и жди
решения о коммите и мердже — сам не коммить.
