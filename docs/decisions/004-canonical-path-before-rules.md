# 004. Почему правила путей судят канонический путь, а не переданную строку

## Context

`pathSecurity` в профиле обещает простую вещь: перечисленные каталоги закрыты
(или наоборот, открыты только они). Обещание не выполнялось — правило
сравнивалось с той строкой, которую передал вызывающий, а до файла эта строка
доходит уже другой.

Замер на лаборатории с профилем `deniedPaths: ['/root']` и белым списком
`/var/log`:

| Путь | Ожидание | Что было |
|---|---|---|
| `~/secret` под root | отказ | **содержимое файла в ответе** |
| `secret` (относительный) | отказ | проходил |
| `//root/secret` | отказ | проходил |
| `/var/log/../../root/secret` | отказ | проходил |
| ссылка из `/var/log` в `/root` | отказ | проходила |
| `/var/logs-of-someone-else/x` | отказ | проходил |
| `/rootkit/x` | проход | отклонялся |

Первая строка — не теория: `ssh_log_tail` вернул содержимое запрещённого файла
на обоих контейнерах. Валидатор подставлял вместо `~` выдуманный `/home/user`,
и под root запрет `/root` не срабатывал вовсе.

Причина у всех семи строк одна: сравнивалась строка, а не путь. Тильда,
рабочий каталог, `..`, сдвоенный слэш и символическая ссылка — пять разных
способов назвать один и тот же файл другим именем, и правило видело имя.

Отсюда же и `/rootkit`: `startsWith('/root')` не знает про границу каталога.

Замер на трёх узлах (alpine/BusyBox, debian/coreutils, router/dropbear)
определил, чем канонизировать:

| | BusyBox | coreutils | dropbear-узел |
|---|---|---|---|
| `readlink`, `realpath` | есть | есть | есть |
| `pwd` = `$HOME` | да | да | да |
| `readlink -f`, нет последнего компонента | печатает путь | печатает путь | печатает путь |
| `readlink -f`, нет каталога в середине | пусто | пусто | пусто |
| `realpath -m` | нет опции | работает | нет опции |
| ответ про корень | `//root/x` | `/root/x` | `//root/x` |

## Decision

**Правило применяется к каноническому пути и только к нему.** Канонический —
абсолютный, без ведущей `~`, без `.`, `..` и сдвоенных слэшей. Тильда в середине
пути каноничности не мешает: раскрывается только ведущая, а в имени файла `~` —
обычный знак, и такие имена на серверах есть. Приведением занимается
`src/managers/path-guard.ts` — единственная дверь; валидатор неканонический
путь судить отказывается, а не додумывает.

Три источника знания, каждый на своём уровне:

- **локально** — тильда, `.`, `..`, сдвоенные слэши;
- **паспорт** — домашний каталог, одна проба за сессию из кэша; относительный
  путь достраивается от него, потому что рабочий каталог неинтерактивной
  команды и есть дом;
- **сервер** — куда ведут символические ссылки, одна проба на путь.

**Правило применяется дважды: к имени и к назначению.** Запрещает любое из
двух. Иначе ссылка внутри разрешённого каталога выносит данные куда угодно,
оставаясь по имени законной.

**Сравнение идёт по границе каталога**, а не по началу строки: `/root` закрывает
`/root/secret`, но не трогает `/rootkit`.

Четыре исхода разбора, которые не смешиваются:

| Исход | Что значит |
|---|---|
| `ok` | правила сошлись на всём, что удалось выяснить |
| `rewritten` | путь пришлось привести к другому виду (раскрыта тильда) |
| `unverified` | по имени сошлось, назначение выяснить нечем — работа идёт, человек предупреждён |
| `denied` | правило не пускает |

**В команду уезжает путь с раскрытой тильдой, а не свёрнутый.** `..` считается
после перехода по ссылке: `/tmp/probe/link/../x` сервер понимает как `/x`, а
лексическая свёртка даёт `/tmp/probe/x`. Канонический вид служит суждению,
операция идёт по адресу вызывающего.

**Резолв на сервере — способ подъёма к предку.** `readlink -f` молчит, если в
середине пути нет каталога, а писать в ещё не созданное дерево приходится
постоянно. Поэтому хвост снимается до ближайшего существующего предка,
резолвится он, и хвост возвращается на место — ссылка в середине так всё равно
раскрывается.

## Alternatives

**Отклонять все неабсолютные пути.** Отвергнуто: закрывает одну строку из семи
и сужает работающую функциональность — относительные пути ходят и сейчас.

**`realpath -m`, не требующий существования пути.** Отвергнуто: опции нет у
BusyBox, то есть нет на роутере и половине встраиваемых систем.

**Отправлять на сервер канонический путь.** Отвергнуто: это подмена адреса.
Свёрнутый `..` через ссылку указывает на другой файл — замер выше.

**Отказывать, когда сервер не может резолвить путь.** Отвергнуто: сервер без
`readlink` — обычный роутер, а не угроза. Правило по имени продолжает работать,
исход помечается как `unverified`, и пробел виден в ответе.

**Спрашивать сервер всегда.** Отвергнуто: лишний RTT на каждую операцию у
профилей, которые правил не задавали вовсе. Проба идёт только при заданном
`pathSecurity`.

**Резолвить ссылки локально.** Невозможно: назначение ссылки — данные удалённой
файловой системы, взять их локально неоткуда.

## Consequences

- Единственный вход — `resolveRemotePath` из `src/managers/path-guard.ts`
  (бывший `remote-home.ts`, переехал целиком). Инструменты про порядок
  «привести → судить» знать не обязаны.
- `PathValidator` перестал нормализовать что-либо: он сравнивает и отказывается
  судить неканоническое. Угадывания в нём больше нет.
- Проверено живьём на двух серверах: 26 утверждений в
  `tests/live/path-rules.live.test.ts` — семь строк таблицы плюс обратная
  сторона (ссылка внутрь разрешённого, `..` внутри него же, запись в ещё не
  созданное дерево). Утверждения смотрят на утечку содержимого, а не на текст
  ошибки.
- Исходы, которые живьём не воспроизвести (сервер без `readlink`, сдвоенный
  слэш в ответе), покрыты юнитами `tests/unit/path-guard.test.ts`.
- Остаётся граница, которую канонизация не закрывает: между проверкой и
  операцией ссылку можно подменить. Для этого нужен доступ к серверу, где
  правила профиля уже не главная линия обороны.
- `ssh_exec` правилами не покрыт: команда — не путь. Ограничения на неё живут в
  правах учётной записи и в отказе от разрушительного удаления (ADR-003).
