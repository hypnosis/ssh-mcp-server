# 010. Чем отвечают `sudo` и почему это поле профиля, а не помощник на сервере

## Context

`sudo` спрашивает пароль у терминала. Терминала у одноразовой команды нет, поэтому
ответ уходит на стандартный ввод: `sudo -S -p ''`, пароль первой строкой. Так это
работает с CORE_22.

Брали пароль оттуда же, откуда пароль входа, — из поля `password`. Это закрывало
профили, которые входят по паролю, и оставляло без хода третью группу: **вход по
ключу под непривилегированным пользователем**. Пароля входа у такого профиля нет
вовсе, предъявлять `sudo` нечего.

Замер на лаборатории, оба контейнера, три случая:

| Профиль | `sudo` | Чем кончается |
|---|---|---|
| ключ, `NOPASSWD` в sudoers | не спрашивает | проходит |
| пароль входа, `sudo` с паролем | отвечаем паролем входа | проходит |
| ключ, `sudo` с паролем | отвечать нечем | `a terminal is required` |

Третья строка — не редкость, а обычная форма боевого доступа: ключ для входа,
пароль для повышения прав, и это два разных секрета даже там, где оба есть.

## Decision

**Отдельное поле профиля `sudoPassword`** — то, чем отвечают `sudo` на этой машине.
Читается и из файла профилей, и из файла секретов, маскируется в журнале, едет на
стандартный ввод, в `argv` не попадает никогда.

Порядок: `sudoPassword`, а при его отсутствии — `password`. Падение назад
обязательно: парольные профили работают сегодня, и менять их поведение выпуском
поля нельзя.

**Где ответить нечем — говорим об этом сами.** `sudo` советует `-S` и askpass, но
из вызова инструмента до них не дотянуться. Один и тот же текст выдаётся на обоих
путях: фоновая задача им отказывает до запуска, обычный вызов добавляет его рядом
с выводом сервера — рядом, а не вместо: то, что сказал сервер, остаётся на месте.

## Alternatives

**`SUDO_ASKPASS` и `sudo -A`.** Механизм тот же, что уже работает для входа по SSH
(ADR-002), и на первый взгляд просится сюда же. Отвергнуто по месту исполнения:
помощник для `sudo` живёт **на удалённой машине**, а не у нас. Передать ему секрет
можно либо переменной окружения удалённой команды — она видна в `ps` там же, — либо
записью скрипта с паролем на диск сервера. Оба пути хуже стандартного ввода, который
уже есть, уже проверен и ничего на сервере не оставляет.

**Спрашивать пароль у человека на каждый вызов** (заготовка из CORE_14). Отвергнуто:
клиент, который умеет спрашивать, есть не у всех, а работа идёт без человека рядом —
агент запускает пересборку на двадцать минут и уходит. Поле профиля отвечает и в
фоновой задаче, где спросить некого по определению.

**Считать, что пароль входа годится и для `sudo`.** Так было. Отвергнуто замером:
у профиля по ключу его нет, а там, где есть оба, они не обязаны совпадать — и
подстановка не того секрета выглядит как неверный пароль, а не как ошибка настройки.

## Consequences

- Формат профиля прирос одним необязательным полем. Старые профили читаются как
  прежде: без `sudoPassword` источник ответа — `password`, как и был.
- Появился путь, по которому секрет попадает на сервер, поэтому у поля тот же режим,
  что у пароля входа: файл секретов под `chmod 600`, маскировка в журнале,
  предупреждение о секрете, записанном прямо в файле профилей.
- Лаборатория обзавелась третьей группой (`ensure_keyuser` — ключ плюс `sudo` за
  пароль). До этого случай собирался руками на каждый замер и потому не имел сторожа.
- Граница осталась: команда, которая сама читает стандартный ввод, пароля не получает.
  Он приехал бы первой строкой её данных — испорченный файл дороже неудобного отказа.
