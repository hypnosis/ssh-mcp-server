## Блокеры

### Б1. Загрузка под sudo идёт мимо единой точки установки

**Где:** `src/tools/transfer-tool.ts:381-411`, `:475-506` (`sudoInstallFile`)
**Против:** `docs/decisions/001-single-install-point.md:48-52` и `:91`; `src/tools/file-tools.ts:574-585` (там тот же вопрос решён правильно)

Единственное место в коде, где данные попадают на боевой путь не через `src/managers/installer.ts`: файл едет в `/tmp`, оттуда `sudo install <stage> <target>` кладётся прямо на цель. ADR-001 перечисляет это пунктом 5 своих подтверждённых дефектов и отдельно отвергает вариант в Alternatives: «Использовать `install` для sudo-пути. Отвергнуто по факту: он копирует поверх». `file-tools.ts:574-577` на том же месте ставит `cp` во временный путь рядом с целью и дальше идёт через установщик — комментарий там дословно объясняет почему.

Три следствия:

1. **Сохранность.** `install` уничтожает старое содержимое до того, как записано новое. Обрыв или срабатывание таймаута (`timeout: opts.timeoutMs`, `:504`) посреди копирования оставляют на сервере обрезанный файл, а `finally` на `:387-392` тут же сносит `/tmp`-копию. Целой копии на боевом пути не остаётся — инвариант §7 нарушен там, где ADR-001 обещает обратное.
2. **Ответ врёт.** Печатается `atomic: opts.atomic` (`:409`), по умолчанию `true` (`:308`). Инструмент называет атомарной операцию, которая ею не является.
3. **Сверка после перезаписи.** `:393-401` — несовпадение хэша здесь означает, что на боевом пути уже лежат плохие данные. В не-sudo ветке (`:419-444`) то же расхождение оставляет цель нетронутой.

**Проверка:** `transfer-tool.ts:501-505` — единственный вызов `install` в `src/`. Живьём: `ssh_upload {sudo:true, timeout:<мало>}` большим файлом поверх существующего — цель должна остаться прежней, а останется обрезанной.

**Побочно:** `docs/transfer.md:52` защищает `install` («preferred over `cp + chmod + chown`») — третий источник правды, разошедшийся с ADR-001. Правится вместе с кодом.

### Б2. Испорченный профиль исчезает молча и уводит `default` на другой сервер

**Где:** `src/utils/profiles-file.ts:330` (`return { config, errors: [] }`); ошибки копятся на `:206`, `:240-243`, `:262`; ложный комментарий `:318-320`
**Против:** `README.md:138-139`; собственных комментариев кода `:233-234` и `:255-257`

Три проверки профиля (порт, `strictHostKeyChecking`, `pathSecurity`) кладут ошибку в `errors` и выбрасывают профиль. Но если в файле остался хоть один валидный профиль, функция возвращает **пустой** список ошибок. `loadProfilesFromEnv` (`profile-resolver.ts:83-86`) умеет падать на непустом списке — он его никогда не получает.

**Замерено** (скрипт на `loadProfilesFile`, сервер не нужен). Файл `{default:"prod", profiles:{prod:{…,strictHostKeyChecking:"Yes"}, staging:{…}}}`:

```
errors returned: []
profiles kept : ['staging']
default became: staging
```

То же для испорченного `pathSecurity` и для непригодного порта. Дальше любой вызов без явного `profile` уходит **на другой сервер**, и об этом нет ни строки. Именно этот случай README:138 обещает не допускать.

**Почему не покраснели тесты:** `tests/unit/profiles-transport-options.test.ts:118-126` и `:166-182` кладут в файл **один** профиль — тогда `profiles` пуст, и ошибки уезжают наверх ранним возвратом `profiles-file.ts:276-281`. Допишите вторым валидный профиль — тест останется зелёным на дыре. §4 CLAUDE.md в чистом виде.

## Важное

### В3. Сторож разрушительного удаления судит строку, а не путь

**Где:** `src/utils/destructive-command.ts:138-159` (`normalize`, `classifyTarget`); `src/tools/exec-tool.ts:150` не знает про `args.cwd`, который добавляет `ssh-executor.ts:99-101`
**Против:** `docs/decisions/003-destructive-removal-guard.md:29-31`

`normalize` снимает только хвостовые слэши. Прогон `inspectCommand` (чистая функция, локально):

| команда | blocked |
|---|---|
| `rm -rf /etc` | **true** |
| `rm -rf //etc` | false |
| `rm -rf /var/../etc` | false |
| `rm -rf /etc/../etc` | false |
| `rm -rf etc` при `cwd:"/"` | false |
| `( rm -rf / )`, `{ rm -rf /; }`, `sh -c "rm -rf /"`, `xargs rm -rf /` | целей найдено 0 |

Ни в одном случае `followsLink` не поднимается — на сервер не уходит даже запрос резолва, команда едет как есть. Сдвоенный слэш получается склейкой `${base}/` + `/etc`; `..` — обычная форма относительного пути; `cwd` — штатный параметр `ssh_exec`. Симлинк для обхода не нужен.

Это тот же класс, который ADR-004 уже закрыл для `pathSecurity` («сравнивалась строка, а не путь»). Вывод в `destructive-command.ts` не перенесён.

**Проверка:** юнит `expect(inspectCommand('rm -rf //etc', '/root').blocked).toBe(true)` — красный.

### В4. Каталоги из правил профиля сами не приводятся к каноническому виду

**Где:** `src/utils/path-validator.ts:70-78` (`isUnder`), `:164-183`; `src/utils/profiles-file.ts:258-268` проверяет у правила только форму

ADR-004 канонизирует проверяемый путь, но каталог из `deniedPaths`/`allowedPaths` сравнивается как написан в профиле.

**Замерено:** `new PathValidator({deniedPaths:['~/.ssh','/root/']})`
- `/home/deploy/.ssh/id_rsa` → `{valid:true}` — правило `~/.ssh` не совпадёт никогда;
- `/root/secret` → отклонён, то есть механизм выглядит работающим.

Загрузчик такое правило принимает молча: `describePathSecurityProblem` требует только непустую строку. Защита числится включённой и не запрещает ничего — ровно то, ради чего писался ADR-004 и §1 CLAUDE.md.

### В5. README описывает снятый механизм кавычек и обещает нерабочий `allowTraversal`

**Где:** `README.md:900-919` против `README.md:920-928`, `src/tools/file-tools.ts:663-665`, `src/tools/log-tools.ts:376`; и `README.md:122-124` против `src/managers/path-guard.ts:197` + `src/utils/path-validator.ts:139-144`

1. Раздел «Double Quotes (for tilde) … `cat "$HOME/.bashrc"`» описывает способ, которого больше нет: тильда раскрывается у нас, путь всегда уезжает в одинарных кавычках. Через десять строк в том же разделе написано правильно — два источника правды в одном файле.
2. `allowTraversal:false` ищет `..` в строке, а инструменты отдают валидатору только канонический путь (`path-guard.ts:197` → `posixPath.normalize`), где `..` уже свёрнут. Сработать правило не может ни на одном вызове: `new PathValidator({allowTraversal:false}).validate('/etc/passwd')` → `{valid:true}` (нет списков → `hasRules()` ложно → выход на `:151-153`). README показывает это как защиту с примером «`../../../etc/passwd` ❌ rejected».

## Мелочи

### М6. `local_path` — четвёртый элемент семейства «значение не должно начинаться с дефиса»

**Где:** `src/tools/transfer-tool.ts:255` → `:384`/`:423` → `openssh-runner.ts:455` → `src/runner/ssh-args.ts:302-311`
**Пара к:** `ssh-args.ts:97-104` (`assertNotOptionLike`: host, username, privateKeyPath), `shell-arg.ts:72-80` (owner), `shell-arg.ts:98` (pattern)

`normalizeLocalSpec` ставит `./` только из-за двоеточия. Локальный путь — первый позиционный аргумент `scp`, и ведущий дефис делает его опцией. Проверено локально: `scp -q -oNotARealOption=1 src dst` скопировал `src` в `dst`, то есть первый аргумент съеден как опция.

Смягчает: `handleUpload` делает `stat(localPath)` до передачи (`:262`), поэтому имя вида `-oProxyCommand=…` до scp не доедет — нужен реально существующий файл с ведущим дефисом (`-r`, `-O`), и тогда меняется режим передачи, а не исполняется чужая команда. Скачивание не затронуто: цель всегда `.upload-<rand>.…` (`tmp-name.ts:13-22`). Цена правки — одна строка.

### М7. `ssh_log_search` объявляет шаблоны, которых не поддерживает

**Где:** `src/tools/log-tools.ts:80` (схема: «glob pattern (*.log)»), `README.md:426`; путь уезжает через `buildSafePath` → `shellQuote` (`log-tools.ts:376`)

`path: "/var/log/nginx/*.log"` → `grep … '/var/log/nginx/*.log'` → код 2 и отказ «No such file or directory». Отказ громкий, данные не страдают, но форма ввода обещана и не работает. Соседний `ssh_file_list` тот же случай держит через `shellGlob` (`file-tools.ts:638`) — способ в проекте есть. Либо провести так же, либо убрать обещание из схемы и README.

### М8. Шапка спринта разошлась с его же чекбоксом

**Где:** `docs/sprints/planned/CORE_11_ssh2_removal.md:3-4` против `:822` и `:923-929`

Статус говорит «в чанке 4 осталась задача 4.12 … осталась граница чанка — общий прогон мутаций», а 4.12 помечена `[x] сделано (2026-08-08)`, и замер границы записан ниже в том же файле и в `TD-01:87-108`. Единый источник правды противоречит сам себе — случай из ADR-005.

### М9. Два поля контракта, которые никто не заполняет и не читает

**Где:** `src/runner/types.ts:44` (`ExecResult.timedOut`), `src/runner/error-classifier.ts:31` (`SpawnOutcome.timedOut`)

`ExecResult.timedOut` записывается ровно один раз и всегда как `false` (`openssh-runner.ts:349`) — таймаут уходит исключением; читателей нет. `SpawnOutcome.timedOut` не передаётся ни одним из двух вызывающих (`openssh-runner.ts:328-331`, `:477-480`) и не читается внутри `classifySpawnOutcome`. Класс TD-10 («компилятор не видит неиспользуемое поле интерфейса»), но в реестре эти два не названы: TD-11 перечисляет экспорты, не поля.

## Что проверено и в порядке

**ADR-001** — протокол `installer.ts:97-173` держится: разведка до единого изменения, staging рядом с целью, права до замены (`:149`), откат через `restore` и запрет уборки при `lastCopyAtRisk` (`:162-166`), `mv -T` и отсутствие `--` в `test` (`remote-path-ops.ts:51-56`, `:96`), следы называются и не трогаются (`:280-298`). Отступает только sudo-ветка `ssh_upload` — Б1.

**ADR-002** — обе дороги к askpass на месте и живые (`askpass.ts:97-105`), порог 8.4 проверяется `assertProfileSupported` (`runtime-check.ts:208-226`) и зовётся и в `exec`, и в `transferOnce` (`openssh-runner.ts:95`, `:446`), секрет только в окружении, скрипт встаёт на место переименованием (`askpass.ts:50-55`).

**ADR-003** — врезка до первой отправки и на весь вызов (`exec-tool.ts:150-153`), маркер описан в `description` (`:86`), «нечем проверить» = отказ и для раскрытия сервером (`destructive-command.ts:196-204`), и для сервера без `readlink` (`removal-guard.ts:57-64`), резолв только для целей со слэшем/`*`, три `rm`-шаблона из `DANGEROUS_PATTERNS` убраны. Отступление — только разбор написания пути, В3.

**ADR-004** — единственная дверь `resolveRemotePath`, порядок «раскрыть → судить» соблюдён во всех инструментах (`file-tools.ts:238,375,626`, `log-tools.ts:370`, `transfer-tool.ts:257,686`), правило применяется дважды — к имени и к цели (`path-guard.ts:207-228`), сравнение по границе каталога, в команду уезжает нераскрученный `expanded.path`, `unverified` — успех с пометкой, `~user/` отклоняется. Дыра только со стороны самих правил — В4.

**ADR-005** — `tests/unit/source-hygiene.test.ts` в наборе и зелёный, управляющих байтов в исходниках нет (поиск по `openssh-runner.ts` находит содержимое), `configFingerprint` использует escape-последовательность (`openssh-runner.ts:523`).

**ADR-006** — `control-sockets.ts` отдаёт только факты, остаток срока не вычисляется (`idleWindowSec`, `index.ts:42-51`), состояний три и `unknown` не смешан с `stale` (`probeSocket:43-57`), `resolveControlPersistSec` — один источник на трёх потребителей (`ssh-args.ts:158`, `control-sockets.ts:104`, `openssh-runner.ts:232`), отбор по префиксу `s-`, на выходе соединения не закрываются.

**§7 сохранность** — держится везде, кроме Б1: `plan.verify` при расхождении уносит только staging (`installer.ts:150-155`), скачивание пишет в staging и подменяет переименованием (`transfer-tool.ts:770-788`), `local-path-ops.rename` ведёт себя как `mv -T`.

**§7 честный ответ** — три исхода разведены и не смешиваются (`remote-verify.ts:68-71`, `:180-184`), «нечем» попадает в ответ как `sha256: skipped — …` (`transfer-tool.ts:338-339`), `file-tools.ts:514-517` на `unavailable` не рушит исправную запись.

**§7 неполный ответ** — `truncated` доезжает от `process.ts:182,195` через `ssh-executor.ts:116` до инструментов; в сверке обрезка читается как «нечем» **в обоих** циклах `collectRemoteHashes` (`:256`, `:268`), как и коды сторожа `[124, 143]` (`:253`, `:267`); `ssh_file_read` на обрезке отказывает, а не отдаёт кусок (`:262-264`, `:300-307`).

**Семейство «путь разбирает shell»** — `prepareRemotePath`/`escapeRemotePath` (`ssh-args.ts:265-282`) закрывают пробел, `*`, `$( )`, обратный слэш, кавычку; перевод строки в классическом протоколе отклоняется явно, в SFTP-режиме уезжает целым; `literal`/`glob`/`shell` выбираются по режиму клиента и направлению (`:347`).

**Пары и списки** — коды сторожа в обоих местах, оба цикла сверки, обе переменные askpass, обе дороги отката передачи (`openssh-runner.ts:420-429`), `-P`/`-p` у scp и ssh.

**Реестр долга** — TD-01…TD-11 прочитаны до отчёта, расхождений с фактом не нашёл: записи TD-06…TD-10 совпадают со строками, которые в них названы.

## Решения владельца по находкам (2026-08-08)

- **Б1 — чиним.** `sudoInstallFile` убирается, sudo-загрузка идёт через `installer` с `remotePathOps({sudo:true})`; staging наполняется так же, как это уже делает `file-tools.ts:574-585`; `mode`/`owner` применяются в `finalize` до замены. ADR-001 не меняем — код возвращается к нему.
- **В3 — доделываем полностью, а не заплаткой.** Узел сначала проектируется отдельно (проект → `docs/drafts/design-removal-guard-parser.md`), потом реализуется. Требование владельца: опереться на то, как задачу решают взрослые инструменты и что говорит спецификация, а не изобретать. Причина отдельного захода: узел чинили несколько раз, и каждый раз находилась новая обходная форма.
- **В4 — правило вида `~/.ssh` или относительное считается ошибкой профиля**, а не тихо нормализуется: молча подставить чужой дом — то же угадывание, которое запретил ADR-004. Ошибка доедет до вызывающего благодаря Б2.
- **В5 — поле `allowTraversal` в профиле остаётся** (пакет в npm, формат не ломаем), README приводится к факту.
- **Модель:** опус на Б1, Б2, В3, В4; sonnet на документы и мелочи.
