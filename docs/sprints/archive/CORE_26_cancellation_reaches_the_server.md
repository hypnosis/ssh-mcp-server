# CORE_26. Отмена доходит до сервера

**Дата:** 2026-08-23
**Статус:** ✅ закрыт
**Закрывает:** [TD-08](../../tech-debt/archive/cancellation-not-wired_08.md)
**Решение:** [ADR-012](../../decisions/012-cancellation-reaches-the-server.md)

## С чего начали

Отменённый вызов бросал клиента `ssh` у нас и оставлял команду работать на сервере. Это
было названным ограничением: README, CHANGELOG, запись долга. Причина в записи —
«закрытие канала не убивает то, что за ним стоит», а ближайшим решением назывался сторож
внутри обёртки, который следил бы за родителем и снимал группу процессов при обрыве.

## Что показал замер

Сторож по родителю работает только без мультиплексирования. Оно у нас включено всегда.

| Проба, оба контейнера | без мультиплексирования | с мультиплексированием |
|---|---|---|
| Родитель команды после обрыва | умер, команда сирота | **жив**, пока жив master |
| EOF на stdin | приходит сразу на старте | то же |
| Ошибка записи в stdout | не возникает | не возникает |
| Команда доживает до конца | да | да |
| Снятие вторым вызовом по поднятому master | — | 30–36 мс, группа умирает |

Пассивного признака обрыва у команды нет вовсе. Значит снятие может быть только активным:
клиент, отменяя вызов, сам говорит серверу остановить работу.

## Что ещё опровергнул замер по дороге

**Отметка в окружении не годится.** Первая написанная версия клала маркер в
`SSH_MCP_CALL=…` перед командой. Живой тест упал на `sudo`, и замер объяснил почему:
`/proc/<pid>/environ` закрыт для всех, кроме самого процесса, — на чтение чужого нужны
права ptrace, которых нет ни в контейнере, ни на ужатом ядре, **root в том числе**.
Отметка переехала в аргументы: `cmdline` читается кем угодно.

**Отметка в аргументах пропадает, если оболочка себя заменяет.** На BusyBox `sh -c
'sleep 25' sh <отметка>` оставляет ровно один процесс с отметкой — сторож времени, который
команде уже не родня: `ash` для последней команды делает `exec`. Тест этого не поймал бы,
потому что команда в нём была составная. Лечится `exit $?` отдельной строкой; отдельной —
потому что после команды, оканчивающейся на `&`, точка с запятой это синтаксическая ошибка.

**Новая группа процессов не нужна.** `setsid -w` на BusyBox нет вовсе, `bash` на alpine не
установлен, а группа у команды и так своя — её выдаёт sshd, и в неё же попадает дерево под
`sudo` на обоих контейнерах.

**Снятие находило само себя.** Оболочка склеивает разорванную в исходнике отметку, поэтому
работающий `grep` несёт её целиком в своих аргументах. Без проверки «своя группа» цикл
убивал бы себя на полпути, оставляя цель живой.

## Что сделано

- `src/runner/cancel-command.ts` — построение команды снятия: поиск по `cmdline`, группа из
  `/proc/<pid>/stat` после закрывающей скобки, `kill -TERM -<pgid>` без `--`, обход своей
  группы, форма под `sudo` с паролем и без.
- `src/runner/openssh-runner.ts` — отметка и `exit $?` в обёртке, снятие в ветке отмены
  отдельным вызовом со своим сроком и без сигнала отмены.
- `src/runner/types.ts`, `src/managers/ssh-executor.ts` — вызов сообщает транспорту, что
  идёт с повышением прав: снятие под `sudo` иначе не доходит до процессов root.

## Проверка

- Юниты: 2751 → 2778. Мутации по новому: `cancel-command.ts` — 24 убито, 0 выжило; новые
  методы транспорта — 37 убито, 1 эквивалентный (`?.` прикрывает случай, недостижимый
  после чтения паспорта); правка в `ssh-executor.ts` — 2 убито, 0 выжило.
- Первый прогон мутаций нашёл девять живых мутантов в снятии: не проверялись язык команды,
  пароль и предупреждения в журнал. Все закрыты тестами.
- Живая сетка: 33 файла, 443 → 447 тестов, зелёная на обоих контейнерах. Форма обёртки
  сменилась у **каждой** команды, поэтому гонялась вся сетка, а не только отмена.
- `tests/live/cancellation.live.test.ts`: прежний тест «команду на машине не снимает»
  покраснел и заменён тремя — обычный вызов, `sudo` без пароля, `sudo` с паролем.
- Следов на контейнерах не осталось: ни процессов с отметкой, ни меток на диске.

## Второй заход: машины, до которых снятие не дошло

Первая редакция оставляла без снятия сервер без `timeout` (отметка ехала внутри обёртки
сторожа) и машину без `/proc` (искать было нечем). Это одна и та же машина: на macOS нет ни
`/proc`, ни `timeout`, а `ps` и `pgrep` есть.

| Проба | macOS | BusyBox | coreutils |
|---|---|---|---|
| `ps -Ao pid,pgid,args` | да | да | да |
| своя группа через `awk` по `$$` | да | да | да |
| `kill -TERM -<pgid>` снимает цель | да | да | да |
| `ps -o pgid= -p $$` | да | **нет** | да |

Отсюда две правки: отметка ставится независимо от сторожа времени, а поиск идёт через `ps`
там, где `/proc` не читается. Ветку выбирает сам сервер — по тому файлу, который читает
первая: у procfs FreeBSD есть `cmdline`, но `stat` нет вовсе, и проверка каталога увела бы
туда, где работать нечем.

Проверено: команда снятия, построенная кодом, снимает цель на macOS; живой тест гоняет
`ps`-ветку принудительно на обоих контейнерах, с контрольным прогоном без снятия — иначе
он зеленел бы оттого, что цель не запустилась. Ручная мутация (`kill` убран из `ps`-ветки)
красит его на обоих контейнерах. Мутации: `cancel-command.ts` — 32 убито, 0 выжило;
`wrapCommand` — 20 убито, 0 выжило. Первый прогон нашёл настоящую дыру: проверки на `kill`
и на пустую группу находили строку в `ps`-ветке и пропажу той же строки из `/proc`-ветки не
замечали — правило №4 в чистом виде.

## Что осталось названным ограничением

Передача файлов и снимок системы отмену не берут — у замены есть окно без целой копии, а
сорванный снимок вернулся бы пустотами вместо отказа.

FreeBSD не проверялась: корректная работа там не гарантируется.

На macOS проверена команда снятия, а не весь путь от вызова инструмента: сквозного прогона
по SSH не делалось.
