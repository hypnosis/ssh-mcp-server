## 🗺 ПЛАН (утверждён 2026-08-02, приводится без изменений)

### Контекст

Две несвязанные проблемы, у которых оказался общий корень.

**Первая — fail2ban.** Агенты открывают новое SSH-подключение почти на каждый вызов инструмента. Пул соединений в проекте есть (`src/managers/connection-pool.ts`, ~550 строк), но не работает: `IDLE_TIMEOUT` захардкожен в 30 секунд (`:76`), а пауза «агент думает» между вызовами почти всегда длиннее. Плюс восемь дефектов — зомби-записи после `'error'` без очистки Map (`:411-414`), гонка retry-таймаута 10 с против `readyTimeout` 30 с (`:279-288` vs `:445`), недосчёт `activeCommands` у ожидающих lock (`:138-142`), расщепление ключа пула (`exec-tool.ts:118` даёт `'default'`, `monitoring-tool.ts:162` — реальное имя профиля).

Но даже идеально починенный пул упирается в потолок: он живёт **внутри процесса**, а stdio-транспорт означает отдельный процесс MCP-сервера на каждое окно Claude Code. Три окна — три SSH-сессии, сколько ни чини.

**Вторая — таймауты и интерактив.** Любая команда, запросившая ввод (пароль sudo, `apt` без `-y`, подтверждение host key), висит до таймаута: PTY не запрашивается нигде, `stream.write` не вызывается ни разу во всём `src/`. Хуже: текст ошибки содержит слово «timeout», предикат ретрая на это срабатывает (`retry.ts:152-158`) и зависшая команда перезапускается ещё дважды — до трёх живых копий и ~90 с вместо 30. Для `mv`/`rm`/установки пакета это риск повторного выполнения. Отдельно: SFTP не имеет таймаутов вообще (`transfer-tool.ts:413/746/824`) и может висеть бесконечно.

**Решение обеих — отказаться от самописного пула в пользу штатного механизма OpenSSH.** ControlMaster мультиплексирует соединения **между процессами** через управляющий сокет в файловой системе: первый вызов открывает master, все последующие — из любого окна, любого субагента — переиспользуют его. Ноль новых TCP, ноль записей в `auth.log`. Заодно интерактивность становится почти бесплатной: `ssh` — дочерний процесс, у него обычные stdin/stdout, а `-tt` даёт настоящий PTY.

Проверено локально: OpenSSH_10.2p1, ControlMaster поддерживается. На нативном Windows не поддерживается (нет передачи fd через unix-сокеты) — там деградация до одиночных соединений, всё остальное работает. Бэкенд остаётся один.

**Про «современный MCP».** Транспорт в спеке описывает канал между Claude Code и процессом с инструментами, а не между сервером и тем, чем он управляет. Наш сервер локальный, для него stdio — штатный выбор по спеке 2025-11-25; Streamable HTTP предназначен для серверов, живущих по URL. Современность здесь берётся из SDK (`0.6.0` → `1.30.0`) и новых примитивов: elicitation, `structuredContent`, `isError`, JSON Schema 2020-12. Вариант «поставить сервер на VPS и ходить в него по HTTPS с OAuth» рассмотрен и отклонён: такая машина держала бы ключи ко всему парку и торчала в интернет — цена не покрывает выгоду для одного пользователя. Записать в ROADMAP как осознанное решение.

**Ограничения.** Пакет опубликован в npm, есть внешние пользователи → формат профилей не менять, имена и параметры инструментов сохранить, выпускать как major с миграционной секцией. Тестов на ядро нет вообще (`tests/unit` покрывает только утилиты) — это главный риск рефакторинга, тесты пишутся до кода.

## Спринт 1 — транспорт на OpenSSH с мультиплексированием

Цель: одна аутентификация на 10-минутное окно при десятках вызовов из нескольких окон Claude Code.

### 1.1 Граница между инструментами и транспортом

Новый `src/runner/command-runner.ts` — интерфейс `CommandRunner`:

```ts
exec(command, opts): Promise<ExecResult>   // НЕ бросает на exitCode ≠ 0
upload(local, remote, opts): Promise<void>
download(remote, local, opts): Promise<void>
ping(opts): Promise<{ ok, masterWasActive, latencyMs }>
stats(): Promise<RunnerStats>
closeMaster(): Promise<void>
```

`ExecResult` — `{ stdout, stderr, exitCode, timedOut, durationMs }`, честно и раздельно. Сейчас `ssh-executor.ts:81-85` всегда возвращает `stderr: ''` и `exitCode: 0`, из-за чего ветки обработки ненулевого кода в инструментах (`exec-tool.ts:160`, `log-tools.ts:164,280`, `snapshot-tool.ts:233`, `file-tools.ts:437`) — мёртвый код. Честный результат их оживляет и попутно чинит `ssh_log_search`: `grep` без совпадений возвращает 1, сейчас это ошибка вместо «0 совпадений».

Инструменты не меняются — они уже строят строку команды и зовут `executor.execute()`. `sudo` остаётся на уровне построения команды (`ssh-executor.ts:62-64`), в интерфейс не входит. Экранирование, tilde expansion, `path-validator.ts` — не трогаем.

`ExecOptions` включает `idempotent?: boolean` (default `false`) и `signal?: AbortSignal`.

### 1.2 Аргументы ssh — `src/runner/ssh-args.ts`

Чистые функции, спавн через `spawn('ssh', args, { shell: false })` — никакого локального shell.

Ключевое:
- `ControlMaster=auto`, `ControlPath=<dir>/s-%C`, `ControlPersist=600`. Каталог — `~/.ssh/ssh-mcp/` с правами 0700, override через `SSH_MCP_CONTROL_DIR`. Не `/tmp`: предсказуемое имя в разделяемом каталоге — риск подмены сокета. `%C` даёт 40-символьный хэш, путь укладывается в лимит unix-сокета 104 символа на macOS.
- `ServerAliveInterval=15`, `ServerAliveCountMax=3` — master сам замечает мёртвый peer за ~45 с. Штатная замена самописному `client.exec('echo keepalive')` каждые 10 с, который к тому же форкал shell на сервере.
- `StrictHostKeyChecking=accept-new`. Сейчас host key не проверяется вообще — в `connect()` (`connection-pool.ts:441-446`) нет `hostVerifier`. `accept-new` строго улучшает безопасность, не ломая первое подключение. Новое опциональное поле профиля `strictHostKeyChecking` для тех, кому нужен `yes`.
- `LogLevel=ERROR` — убирает шум вида «Permanently added…», иначе он ломает классификатор ошибок.
- `IdentitiesOnly=yes` + `IdentityFile` только когда `privateKeyPath` задан — важно для fail2ban: без этого клиент перебирает ключи по очереди, и каждый отвергнутый sshd считает неудачной попыткой.
- `BatchMode=yes` только когда нет ни `password`, ни `passphrase`. Для парольных профилей `BatchMode` отключает все запросы, включая askpass, — ставить нельзя.
- `~/.ssh/config` по умолчанию читается (CLI-опции всегда побеждают конфиг), что бесплатно даёт ProxyJump и ssh-agent. Опциональное поле профиля `ignoreUserConfig` → `-F /dev/null`.

На win32 блок ControlMaster опускается, один warn при старте.

### 1.3 Пароли и passphrase — `src/runner/askpass.ts`

Обратная совместимость: профили npm-пользователей могут содержать `password`, а `ssh` CLI пароль со stdin не берёт. Механизм — `SSH_ASKPASS` + `SSH_ASKPASS_REQUIRE=force` (OpenSSH ≥ 8.4, подтверждено в `man ssh`): ssh сам запускает указанный исполняемый файл, тот печатает секрет в stdout. Работает и для пароля, и для passphrase ключа, без TTY.

Путь секрета: статический скрипт `~/.ssh/ssh-mcp/askpass.sh` (0700), печатающий `$SSH_MCP_SECRET`; сам секрет передаётся в env дочернего `ssh`. **В argv секрет не попадает никогда** — иначе виден в `ps`. В env он виден только владельцу процесса и root, то есть тот же уровень доверия, что и JSON-файл профилей с паролем внутри. На диск не пишется.

Выигрыш от мультиплексирования: пароль вводится один раз при подъёме master, следующие 10 минут команды идут без аутентификации.

Если `ssh` < 8.4 и профиль парольный — понятная ошибка при обращении к этому профилю (не падение всего сервера).

### 1.4 Жизненный цикл master

Ленивый подъём: никакого `ssh -M -N -f`, первая команда с `ControlMaster=auto` сама становится master. Внутрипроцессный промис-лок «первая команда профиля выполняется одна» (~15 строк, замена `locks` из `connection-pool.ts:60`) убирает гонку двух параллельных вызовов.

- Проверка — `ssh -O check` (только в `stats()`/`ping()`, не перед каждой командой).
- Гашение — `ssh -O exit`: при смене конфига профиля (замена `hasConfigChanged`, `connection-pool.ts:494-501` — иначе master продолжит ходить со старыми учётными данными) и по новому действию `ssh_monitor { action: 'disconnect' }`.
- В shutdown (`index.ts:168-183`) ничего не гасим — master переживает рестарт MCP-сервера, это выгода.
- `ssh_monitor stats` (`monitoring-tool.ts:78-114`) переписывается: backend, версия ssh, включено ли мультиплексирование, по каждому профилю — master running (pid), controlPath, счётчики. Метрики пула умирают вместе с пулом.
- Edge: при упоре в `MaxSessions` сервера ssh пишет `mux_client_request_session` — классификатор распознаёт и делает один повтор с `ControlMaster=no`.

### 1.5 Таймауты, отмена, ретраи

Один таймер на операцию: истёк → `SIGTERM` дочернему ssh, через 5 с → `SIGKILL`. `AbortSignal` — тот же путь немедленно. `Promise.race`, оставляющий операцию висеть (`retry.ts:76-83`), удаляется.

Честно про удалённую сторону: убийство локального ssh закрывает канал, но без PTY удалённый процесс может пережить это. Поэтому при заданном таймауте команда префиксуется удалённым `timeout <N+5>s`, если на хосте есть `timeout` (feature-detect один раз на профиль). Локальный kill — гарантия для нас, удалённый `timeout` — гигиена для сервера.

Классификация — `src/runner/error-classifier.ts`, по `exitCode` и паттернам stderr: `SSHAuthError`, `SSHHostKeyError`, `SSHTransportError`, `SSHTimeoutError`, `SSHBinaryMissingError`. Ненулевой код удалённой команды — не ошибка, а нормальный `ExecResult`.

Политика ретраев (замена `createSSHRetryPredicate`, `retry.ts:130-165`, где дефолт `return true` ретраит вообще всё): ретраится **только** `SSHTransportError` и **только** при `idempotent: true`, две попытки. Таймаут не ретраится никогда. `idempotent: true` проставляется точечно read-only вызовам (`ssh_file_read`, `ssh_log_*`, snapshot, audit, пробы monitor).

### 1.6 Передача файлов

`scp` через тот же ControlPath — есть везде, где есть ssh; с версии 9.0 внутри это SFTP-протокол (binary-safe); принимает те же `-o`, значит переиспользует master. `rsync` не гарантирован на удалённой стороне, `sftp -b` — второй парсер ошибок ради ничего.

Заменяются: `transfer-tool.ts:384-428` (upload), `:735-780` (download), `:782-841` (рекурсивная загрузка — один `scp -r` вместо ручного обхода `readdir`, минус ~60 строк), `file-tools.ts:494-629` и `:635-664`, `monitoring-tool.ts:162-176` → `runner.ping()`.

`uploadDirectory` (`:499-621`): staging и atomic mv сохраняются, но verify становится батчевым — локальный манифест `sha256sum`, на сервере `sha256sum -c -` через stdin. Быстрее и надёжнее текущей поштучной проверки.

Sudo-upload (`{sudo: true, mode, owner}`) не меняется — он построен на staging + `sudo install` поверх `executor.execute` (`transfer-tool.ts:291-320`).

Теряется: программный прогресс передачи (наружу он всё равно не репортится) и параметры `concurrency`/`chunkSize` — остаются в схеме для совместимости, игнорируются с пометкой deprecated.

### 1.7 Тесты

Три слоя:

1. **Чистые юниты без моков** — `ssh-args.test.ts` (матрица: ключ/пароль/passphrase × платформа × опции; обязательный ассерт «секрета нет в argv», «парольный профиль ⇒ нет BatchMode»), `error-classifier.test.ts` (таблица реальных stderr OpenSSH → класс), `retry-policy.test.ts`.
2. **Раннер с моком `child_process`** — happy path, ненулевой exit, таймаут с fake timers (ассерт SIGTERM → 5 с → SIGKILL), AbortSignal, ENOENT спавна, лимит буфера. Основной объём, дёшево и стабильно.
3. **Интеграционные, opt-in** — контейнер `openssh-server`, `-F /dev/null`, изолированный `SSH_MCP_CONTROL_DIR`. Ключевой сценарий: две команды подряд → `ssh -O check` == 0 и в логе sshd **ровно один** `Accepted`. Это прямая проверка исходной проблемы.

### 1.8 Порядок миграции

Флаг `SSH_MCP_BACKEND=openssh|ssh2` с дефолтом `ssh2`, тонкий адаптер `ssh2-runner.ts` поверх текущего кода — оба бэкенда проходят один контрактный набор тестов. Каждый шаг отдельным PR, до предпоследнего поведение по умолчанию не меняется.

Точка невозврата — последний шаг: удалить `connection-pool.ts`, `ssh-manager.ts`, `ssh2-runner.ts`, флаг; `npm rm ssh2 @types/ssh2`.

Выпуск: `2.0.0-beta.N` → дог-фудинг на своих серверах → `2.0.0`. В CHANGELOG миграционная секция: новое требование системного `ssh` в PATH, включённая проверка host key, изменившийся текстовый вывод `ssh_exec` из-за честных кодов; совет пиновать `1.x`, если системного ssh нет.

## Спринт 3 — интерактивный режим и долгие команды

### 3.1 Когда включать PTY

Главный инсайт: большинству интерактивных сценариев PTY не нужен, а PTY — источник хрупкости (сливает stderr в stdout, добавляет ANSI и эхо, ломает бинарный вывод).

- **sudo — без PTY.** В интерактивном пути обёртка становится `sudo -S -p '<SENTINEL>'`, где SENTINEL — случайный токен на вызов. `-S` читает пароль со stdin, приглашение уходит в stderr, stdout остаётся чистым, детекция детерминированная. При NOPASSWD приглашение просто не появляется. Обычная обёртка (`ssh-executor.ts:62-64`) сохраняется для неинтерактивных вызовов.
- **`apt [Y/n]` и подобное — без PTY**, через открытый stdin процесса.
- **PTY (`ssh -tt`) — только при явном `interactive: 'pty'`**, для программ, читающих `/dev/tty`: подтверждение host key, passphrase, dpkg-конфигураторы. Параметры: `TERM=dumb`, `ECHO: 0` (пароль не отражается в буфере). Поверх — stateful ANSI-стриппер, устойчивый к разрыву escape-последовательности между чанками.
- Параметр `interactive: 'off' | 'auto' | 'pty'`, default `auto` **только** у `ssh_exec`. Внутренние вызовы из audit/snapshot/log идут через обычный путь и физически не могут попасть в интерактивный — регресс парсинга исключён конструктивно.
- Автоперезапуска с PTY при ошибке «a terminal is required» **не делаем**: молчаливый повтор неидемпотентной команды опаснее ошибки. Возвращаем внятное «повторите с `interactive: "pty"`».

### 3.2 Детекция запроса ввода

По очищенному от ANSI хвосту буфера, сигналы по убыванию доверия:

1. **Sentinel sudo** — точное совпадение случайного токена, ложное срабатывание исключено: удалённый вывод его не знает.
2. **Паттерн из таблицы в последней строке И буфер не заканчивается переводом строки.** Второе условие отсекает основную массу ложных срабатываний: строка лога `... failed Password: check\n` не матчится. Плюс контекстный гейтинг — парольные паттерны принимаются только если команда содержит `sudo|ssh|scp|git|rsync|passwd|su `.
3. **Тишина потока** ≥ 750 мс после совпадения (программа могла ещё дописывать).

Детектор никогда не отвечает сам — цена ложного срабатывания — лишний вопрос человеку, а не неверный ввод. Лимит 5 запросов на команду.

### 3.3 Elicitation

`src/utils/elicitation.ts` — мост к `server.elicitInput()`. Плоские схемы: пароль (string), подтверждение (enum `['y','n','abort']` — буквально то, что ждёт программа), свободный ввод. В тексте запроса всегда указаны host, профиль, команда и приглашение удалённой программы **как цитата недоверенного вывода**.

**Деградация обязательна.** Перед запуском проверяем `server.getClientCapabilities()?.elicitation`. Если клиент не умеет (Claude Code < 2.1.76 или другой клиент) — при обнаружении запроса ввода немедленно Ctrl-C и завершение с внятной ошибкой: что именно спросил сервер и как обойти (`NOPASSWD` для sudo, `-y` для apt, либо `detach: true`). Никогда не висим.

Безопасность секрета: строка из elicitation сразу оборачивается в `SecretBuffer` (Buffer, `wipe()` через zero-fill, `toString()` → `[REDACTED]`), пишется в канал напрямую из Buffer, скраббер вычищает её из входящих чанков (второй эшелон после `ECHO: 0`). В результат инструмента попадает только пометка «ввод предоставлен через elicitation», в логи — ничего. На диск не пишется.

Prompt injection: удалённый вывод может нарисовать фейковое `[sudo] password for root:`, чтобы выманить пароль. Для sudo закрыто sentinel-токеном. Для остальных — приглашение всегда показывается как цитата недоверенного источника, решение принимает человек, и пароли из профиля **никогда** не подставляются в детектированные приглашения автоматически.

### 3.4 Три таймера

| Таймер | Default | При срабатывании |
|---|---|---|
| Тишина потока без обнаруженного запроса | 30 с | Ctrl-C, «нет вывода 30 с; для долгих команд используйте `detach: true`» |
| Общий wall-clock | 300 с для interactive | Ctrl-C, частичный вывод в ошибке |
| Ожидание ответа человека | 300 с | трактуем как отказ |

Пока запрос к человеку в полёте, первые два таймера **остановлены** — человек не должен убивать команду своей задумчивостью.

### 3.5 Detach для долгих команд

Ответ на «отваливается по таймауту». Состояние целиком на удалённом диске, MCP-сервер stateless: `setsid bash -c '<cmd>; echo $? > exit_code' </dev/null >> output.log 2>&1 &`, pid в файл, каталог `~/.ssh-mcp/jobs/<id>/`. Переживает и рестарт MCP-сервера, и обрыв SSH, и не требует ничего кроме POSIX-шелла (в отличие от screen/tmux, которых может не быть).

Новые инструменты: `ssh_job_status`, `ssh_job_output` (инкрементально по offset — курсор хранит вызывающий, сервер stateless), `ssh_job_kill` (`kill -TERM -- -$pgid`, setsid делает pid равным pgid), `ssh_job_list` с автоочисткой завершённых старше 7 дней. У `ssh_exec` — параметр `detach: true`, взаимоисключающий с `interactive`.

### 3.6 Тесты

Детектор и ANSI-стриппер — чистые юниты, включая обязательные негативные кейсы (строка с `Password:` в середине лога, разрыв escape-последовательности между чанками). Интерактивная сессия — мок канала: happy path sudo с ассертом «пароль не попал ни в `stdout`, ни в аргументы логгера, Buffer занулён», отказ пользователя, клиент без elicitation, все три таймера, обрыв канала во время ожидания ответа.

## Проверка результата

**Спринт 1** — главный критерий, прямая проверка исходной проблемы: включить `LOG_LEVEL=debug`, открыть **два** окна Claude Code, выполнить десяток инструментов с паузами из обоих. На сервере `journalctl -u ssh | grep Accepted` — **одна** запись за 10-минутное окно вместо десятков. `ssh -O check` показывает живой master. Плюс: `ssh_exec("false")` возвращает «Exit code: 1» вместо ошибки после трёх повторов; `ssh_log_search` по строке без совпадений возвращает «0 совпадений»; таймаут убивает ssh, но следующая команда работает мгновенно (master жив).

**Спринт 2** — `npx @modelcontextprotocol/inspector`: все 14 инструментов отвечают; ошибки приходят с `isError`; `ssh_audit_baseline` отдаёт `structuredContent`, а не JSON внутри текста.

**Спринт 3** — `sudo whoami` на профиле без NOPASSWD: всплывает диалог, пароль не виден ни в ответе, ни в stderr-логах при `SSH_MCP_LOG_LEVEL=debug`. `apt-get install` без `-y` — подтверждение. Отказ от ввода корректно прерывает команду. `ssh_exec { command: "sleep 120 && echo done", detach: true }` → мгновенный job id, рестарт MCP-сервера, `ssh_job_status` по-прежнему видит задачу.

Регресс во всех спринтах: `ssh_snapshot` и `ssh_audit_baseline` дают тот же вывод, что до изменений.
