## Зачем этот спринт

Любая команда, запросившая ввод, сегодня висит до таймаута и умирает: `sudo` на профиле без
NOPASSWD, `apt` без `-y`, конфигуратор пакета. Пароль профиля в такие приглашения не
подставляется и подставляться не должен — отвечать обязан человек.

MCP это умеет: клиент может показать запрос ввода (`elicitation`), а сервер — дождаться
ответа. SDK 1.30 уже стоит, ради этого он и обновлялся.

План писался, когда транспорта на OpenSSH ещё не было, поэтому ниже он приведён к нынешнему
коду, а не перенесён копией.

## Что уже лежит в коде

- **`-tt` написан и не подключён.** `buildSshArgs` принимает `requestTty` (`src/runner/ssh-args.ts`),
  юнит его проверяет (`tests/unit/ssh-args.test.ts`), но ни один вызов его не передаёт. Ровно
  тот класс дефекта, который мутации не ловят: код есть, вызывающего нет.
- **Обёртка sudo уже не та, на которую ссылался план.** Сейчас это `sudo <bash|sh> -c
  <экранированная команда>`, язык берётся из паспорта сервера. Значит интерактивная форма —
  `sudo -S -p '<маркер>' <bash|sh> -c '<команда>'`, и кавычки накладываются поверх уже
  существующих. Это семейство, а не один случай: пробел, апостроф, подстановка, перевод строки.
- **Запуск не потоковый.** `runProcess` закрывает stdin сразу и отдаёт вывод по завершении
  процесса. Детекция приглашения, ответ в stdin и таймер тишины требуют второго режима запуска.
- **Секреты в логах вычищает `hideFromLogs`.** Механизм годится для профильного пароля, но не
  для введённого человеком — см. ловушки ниже.
- **Живая сетка с настоящим клиентом поверх настоящего сервера** уже есть
  (`tests/live/structured-output.live.test.ts`) — там же проверяется и диалог ввода.
- **Лаборатории не хватает пользователя.** Есть `deploy` с NOPASSWD и `pwuser` с паролем без
  sudo. Нужен третий: пароль есть, sudo **требует** пароль — иначе весь спринт проверять не на чем.

## 📊 ЗАДАЧИ

### 1. Потоковый запуск — рядом, а не вместо

Второй режим запуска процесса: stdin открыт, вывод приходит кусками, останов по тишине потока
и по общему сроку. Нынешний `runProcess` не трогается: через него ходят все инструменты, а
интерактив нужен одному `ssh_exec`.

**Проверка:** юниты на настоящих процессах, оба таймера и обе ветки останова, мутация руками.

### 2. Пароль sudo через запрос к человеку

Без PTY. Обёртка `sudo -S -p '<маркер>'`: пароль читается со stdin, приглашение уходит в
stderr, stdout остаётся чистым, а маркер — случайный на вызов, поэтому совпадение
детерминированно и подделать его удалённым выводом нельзя.

Запрос к человеку идёт через контекст вызова (`sendRequest` обработчика), деградация —
через объявленные клиентом возможности. Клиент не умеет запрашивать ввод — не висим, а
отказываем с готовым обходным путём: NOPASSWD, `-y`, `detach`.

Параметр `interactive: 'off' | 'auto' | 'pty'` появляется **только** у `ssh_exec`. Внутренние
вызовы из аудита, снимка и логов идут прежним путём и в интерактивный попасть не могут.
`auto` включает `-S`-путь только когда клиент умеет отвечать; иначе обёртка sudo остаётся
прежней знак в знак.

**Проверка:** живая сетка на обоих контейнерах — `sudo whoami` на профиле без NOPASSWD
возвращает `root`; пароль не виден ни в ответе, ни в логах при уровне `debug`; отказ человека
прерывает команду; клиент без поддержки не висит.

### 3. Подтверждения вида `[Y/n]`

Через открытый stdin, без PTY. Приглашение опознаётся по очищенному хвосту буфера: паттерн в
последней строке **и** буфер не кончается переводом строки — второе условие отсекает строки
логов со словом `Password:` в середине. Плюс проверка контекста команды. Детектор никогда не
отвечает сам: цена ошибки — лишний вопрос человеку, а не подставленный ввод. Не больше пяти
запросов на команду.

**Проверка:** негативные юниты (пароль в середине лога, чужой `Continue? [Y/n]` в выводе) и
живой замер установки пакета без `-y`.

### 4. PTY по явному требованию

`interactive: 'pty'` — для программ, читающих терминал напрямую. Здесь подключается `-tt`,
лежащий без вызывающего. Эхо выключается, поверх ставится стриппер управляющих
последовательностей, устойчивый к разрыву последовательности между кусками.

Автоматического повтора с PTY при ошибке «нужен терминал» не делаем: молчаливый повтор
неидемпотентной команды опаснее внятного отказа.

**Проверка:** юниты стриппера с разрывом последовательности между кусками; живая программа,
читающая терминал.

### 5. Три срока

| Срок | Умолчание | При срабатывании |
|---|---|---|
| Тишина потока без обнаруженного запроса | 30 с | Останов, подсказка про `detach` |
| Общий срок интерактивной команды | 300 с | Останов, частичный вывод в отказе |
| Ожидание ответа человека | 300 с | Считается отказом |

Пока вопрос к человеку в полёте, первые два остановлены: человек не должен убивать команду
своей задумчивостью.

## Ловушки, из-за которых спринт и расписан подробно

- **Введённый пароль не регистрируется в списке секретов логгера.** Маскирование идёт
  подстрокой по глобальному множеству, и пароль вроде `root` испортил бы любой лог, где
  встречается это слово. Тот же дефект уже ловили в выводе команд — там от маскировки
  отказались осознанно. Секрет просто никуда не пишется, и это сторожится тестом.
- **Секрет живёт в буфере и зануляется**, в argv не попадает никогда, на диск не пишется, в
  ответ инструмента уходит только пометка «ввод предоставлен человеком».
- **Удалённый вывод недоверенный.** Он может нарисовать поддельное приглашение пароля. Для
  sudo это закрыто случайным маркером; в остальных случаях приглашение показывается человеку
  как цитата чужого текста, и решение принимает он.
- **Регресс sudo-пути.** Обёртку sudo проверяет живая сетка на обоих контейнерах; она обязана
  остаться зелёной без правок — это и есть доказательство, что `auto` ничего не сломал.

## Границы

- `sshpass` и любые секреты в argv — нет.
- Автоматический повтор с PTY — нет.
- Долгоживущие `ssh_session_*` — нет.
- Перевод схем на zod, Streamable HTTP, Tasks — нет.
- Имена инструментов и формат профилей не ломаем.
