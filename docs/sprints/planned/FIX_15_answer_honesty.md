# FIX_15 — ответ обязан совпадать с тем, что произошло

**Статус:** ✅ ЗАВЕРШЁН (2026-08-15)
**Дата заведения:** 2026-08-15
**Ветка:** `feat/openssh-transport`
**Происхождение:** приёмка 02 под живым MCP-клиентом —
ACCEPTANCE_MCP_02, находки MCP-01, 02, 04, 06, 07, 12, 13

---

## Зачем этот спринт

Приёмка нашла четырнадцать расхождений, и семь важных ложатся в один класс: **инструмент
сообщает не то, что произошло на сервере.** Команда выполнилась не в том каталоге и
отчиталась успехом. Снос системного каталога заблокирован, а ответ выглядит как удачный.
Пакетная запись не записала ни одного файла и не помечена ошибкой. Аудит утверждает «служб
ноль» там, где служб нечем сосчитать.

Это опаснее обычной ошибки: неверный ответ не заставляет остановиться. Тот, кто читает
ответ — человек или агент, — идёт дальше и делает следующий шаг на ложном основании.

Спринт закрывает шесть находок этого класса. Косметика и доработки в него **не входят** —
их список в конце.

---

## Что берётся готовым

Ни один приём здесь не изобретается заново: каждый уже написан в этом же коде, просто не
разнесён по соседним местам.

| Готовое | Где | Зачем здесь |
|---|---|---|
| Маркер «утилиты нет» | `audit-tool.ts:222-235` (`NO_UFW`, `NO_IPTABLES`) | Образец для служб и обновлений |
| Распознавание неотвечающего systemd | `audit-tool.ts:873` (`AuditTool.NO_SYSTEMD`) | Готовый образец, применить в аудите и снимке |
| Признание «раздела нет» | поле `unavailable` в ответе аудита | Место, куда пишется причина |
| Проверка «нет такой задачи» | `job-command.ts:162` (`state=missing`) | Образец для вывода и снятия задачи |
| Пометка отказа | общий путь ошибок инструментов (`isError: true`) | Уже работает у таймаута, чтения, профиля |
| Обёртка команды | `ssh-executor.ts:91-99` (`sudo <оболочка> -c`) | Соседняя строка того же места, что чиним в задаче 2 |
| Экранирование | `shellQuote` (`src/utils/shell-arg.ts`) | Ничего своего для кавычек не писать |

## Границы: чего в этом спринте не делаем

Нарушение любой строки — повод остановиться и спросить, а не решать самому.

- **Имена инструментов и формат профилей не трогаем.** Пакет в npm.
- **Типы полей в схеме ответа не меняем.** `services.running_count` и `updates.upgradable`
  объявлены числами (`audit-output.ts:152-208`), и клиент 1.30 сверяет ответ со схемой:
  `null` или строка вместо числа — это `-32602` у вызывающего. Признание «нечем проверить»
  выражается **отсутствием раздела**, а не подменой значения.
- **Работающее не сужаем.** Ни одна задача не должна отнять возможность, которая сегодня
  есть.
- **Соседний код не улучшаем.** Заметил постороннее — записал в конец файла спринта,
  не тронул.
- **Мелочи из приёмки (MCP-03, 05, 08, 09, 10, 11, 14) в этот спринт не входят.** Даже если
  правка на одну строку и файл уже открыт.
- **Ответ «здесь менять нечего» — законный.** Если замер показал, что находка не
  воспроизводится, задача закрывается замером, а не правкой.

## Общая процедура каждой задачи

Одинаковая для всех шести, потому что все шесть — про поведение на сервере, а не про
логику в памяти.

1. **Замер до кода.** Воспроизвести находку на стендах, названных в задаче, и записать
   ответ дословно. Не воспроизвелось — стоп, задача не начинается.
2. **Правка** в названной точке, в пределах названных границ.
3. **Замер после.** Тот же вызов, тот же стенд, ответ дословно. Оба замера — в отчёт
   задачи.
4. **Юнит на новое поведение** и мутация по тронутому: `npm run mutate -- HEAD`. Выживший
   мутант в свежем коде — тест недописан, а не «допустимо».
5. **Живой прогон целиком:** `npm run lab:up`, затем
   `SSH_MCP_LIVE=1 npx vitest run tests/live/` на обоих контейнерах.
6. **Отчёт задачи — diff и вывод команд.** Не «сделано», а чем это видно.

Стенды: `mcp-alpine` (BusyBox, 2231), `mcp-debian` (coreutils, 2232), `mcp-router` (dropbear,
2233). Профили приёмки — `~/.mcp-config/acceptance-profiles.json`, ключ `.lab/key`.

### Решения, принятые при старте работы

Три развилки, которых спринт не касается. Записаны до первой правки, чтобы не выясняться
задним числом.

**Чем меряем «после».** Подключённый `ssh_mcp_2` поднят из `dist/` при старте сессии и после
`npm run build` продолжает крутить старый код до перезапуска клиента — замер по нему покажет,
что починка не сработала. Поэтому замеры «после» идут своей оснасткой, которая каждый раз
поднимает свежий `dist/`, и написана она на `Client` из `@modelcontextprotocol/sdk`, а не на
голом JSON-RPC: это тот же клиент, что сверяет `structuredContent` со схемой, значит задача 4
получает настоящую проверку протокола. Оснастка живёт в scratchpad и в репозиторий не идёт.

**Заголовок пакетного ответа (задача 2).** Форма `Read 1/2 files:` и `Write 0/2 files:` —
одинаково в обоих местах. Значки, разделители и порядок строк не трогаются.

**Форма связки с `cwd` (задача 6).** Выбирается замером, но с предпочтением
`cd <каталог> || exit 1; <команда>`: она не трогает текст команды и её кавычки вовсе, тогда
как вариант со скобками уже давал ловушку на команде, оканчивающейся на `&`. Замер обязан
подтвердить или опровергнуть, а не подтвердить предпочтение по умолчанию.

**Добавка к проверкам задачи 6.** Каркас фоновой задачи ждёт появления pid циклом
(`job-command.ts:150`), а тело с неудавшимся переходом выходит мгновенно. Отдельным пунктом
проверяется, что такая задача не держит ожидание весь лимит попыток и кладёт ненулевой
`exit_code`.

## 📊 ЗАДАЧИ

Порядок не произвольный: сначала дешёвые правки с узкой зоной поражения, потом самая
рискованная. Так к моменту опасной задачи живая сетка уже прогнана и зелёная.

### 1. Отказ сторожа удаления помечается ошибкой (MCP-12)

**Что не так.** `rm -rf /home` блокируется правильно, но ответ приходит без `isError`.
Таймаут, отсутствующий файл и неизвестный профиль пометку получают — блокировка нет.
Читающий по признаку решит, что снос выполнен.

**Точка правки.** `src/tools/exec-tool.ts:195-197` — отказ возвращается как
`{ content: [{ type: 'text', text: refusal }] }`.

**Не трогать.** Текст `blockedMessage` (`destructive-command.ts:231`) — он выверен и
объясняет, как выполнить осознанно. Саму логику сторожа и список защищаемых путей.
Поведение «весь пакет отвергается целиком» (`exec-tool.ts:191-193`) — оно правильное.

**Ловушка.** Тесты закрепляют нынешний ответ:
`tests/unit/exec-destructive-guard.test.ts:67,112,135` и
`tests/unit/exec-detach.test.ts:218`. Их надо привести к новому поведению осознанно —
дописать проверку `isError`, а не ослабить существующие.

**Проверка.** Вызов в обход клиента (в Claude Code такие команды режет классификатор, до
сервера они не доходят) — скрипт по образцу `scratchpad/probe-size.mjs` из приёмки:
`ssh_exec {profile: "mcp-alpine", command: "rm -rf /home"}` на цели, снос которой безвреден.
Было `isError: (absent)`, ожидается `true`, текст не изменился.

### 2. Пакетный вызов признаёт полный провал провалом (MCP-13)

**Что не так.** `ssh_file_read` с двумя несуществующими путями и `ssh_file_write` с двумя
запрещёнными путями отвечают без пометки ошибки, заголовком «Read 2 files» / «Write 2
files». Одиночная форма тех же вызовов пометку ставит.

**Точка правки.** `src/tools/file-tools.ts:371` и `:467` — сборка ответа и заголовок.

**Границы.**
- Пометка ставится **только когда успехов ноль**. Частичный исход (один прочитан, один нет)
  остаётся без пометки: там результат действительно частичный и честно показан значками
  ✓ / ✗.
- Значки, разделители и порядок строк не менять — по ним читают глазами.
- Заголовок должен говорить, сколько удалось, а не сколько обработано. Форму выбрать одну и
  применить к обоим местам одинаково.

**Ловушка.** Два места (`чтение` и `запись`) — правка нужна в обоих, и это ровно тот случай
из §4 CLAUDE.md, когда сторож ставят на первый элемент пары. Тест обязателен на каждое.

**Проверка.** Четыре замера: чтение одиночное и пакетное, запись одиночная и пакетная, все
на заведомо неудачных путях. Ожидается: одиночные — как сейчас, пакетные — `isError: true`
и заголовок с числом удавшихся. Плюс пятый замер на частичный исход: пометки нет.

### 3. Нет такой задачи — это ответ, а не пустой вывод (MCP-01, MCP-02)

**Что не так.** `ssh_job_output` для несуществующей задачи отвечает «0 bytes total …
(no output at this offset)» — неотличимо от живой задачи, которая пока молчит. Достаточно
перепутать профиль. `ssh_job_kill` там же отвечает «never recorded a pid» — сообщение про
другой случай (задача есть, pid не записан).

**Точка правки.** `src/utils/job-command.ts:180-190` (`buildOutputCommand`) и `:200-211`
(`buildKillCommand`) — ни одна не проверяет, что каталог задачи существует. Разбор ответа и
печать: `src/tools/job-tools.ts:198-229` и `:268-287`.

**Образец рядом.** `buildStatusCommand` (`job-command.ts:162`) делает ровно это:
`if [ ! -d "$d" ]; then printf '<маркер> state=missing'; exit 0; fi`. Повторить приём, не
выдумывать свой.

**Границы.**
- Различие «задачи нет» и «задача есть, но пуста / без pid» обязано сохраниться: это три
  разных ответа, а не два.
- Формат курсора (`Next offset`) и его правило не менять — оно выверено и описано
  комментарием на `job-command.ts:177-178`.
- `ssh_job_status` не трогать: он уже отвечает правильно.

**Ловушка.** `test -d` и `printf` идут на BusyBox и dropbear. Проверять на всех трёх
стендах: диалекты уже расходились, из-за этого и заведено правило §3.

**Проверка.** На каждом стенде: выдуманный идентификатор в `output` и в `kill`; затем
реальная задача, ещё ничего не напечатавшая, — она обязана по-прежнему отвечать «вывода
нет», а не «нет такой задачи». Второй замер важнее первого: он сторожит, что починка не
съела законный случай.

### 4. Аудит не считает нулём то, что не сосчитал (MCP-06)

**Что не так.** На `mcp-alpine` нет ни `systemctl`, ни `apt`; на `mcp-debian` `systemctl`
есть, но systemd не отвечает («System has not been booted with systemd as init system»).
В обоих случаях ответ: `services: {failed: [], running_count: 0}`,
`updates: {upgradable: 0}`, `unavailable: []`.

**Точка правки.** `src/tools/audit-tool.ts:212-213` (службы) и `:238` (обновления) — сбор
без маркера; `:336` и `:353` — разбор, который превращает пустой вывод в ноль.

**Образец рядом, в том же файле.** Маркеры `NO_UFW` / `NO_IPTABLES` (`:222-235`) и
распознавание `AuditTool.NO_SYSTEMD` (`:873`), которым уже пользуется `ssh_service_status`.
Оба приёма написаны, проверены и работают — задача в том, чтобы применить их к соседним
разделам.

**Границы — самое важное в этой задаче.**
- **Типы в схеме не менять.** Если раздел удалось выполнить — поля прежние и числовые.
  Если нет — **раздела в ответе нет вовсе**, а причина уходит строкой в `unavailable`.
  Так уже сделано с `docker: null`; корневая схема требует только `unavailable` и
  `red_flags` (`audit-output.ts:217`), остальные разделы необязательны.
- Формулировка причины — как у соседей: коротко и по делу, «no systemctl on the server»,
  «systemd did not answer on this server», «no apt on the server».
- `red_flags` по невыполненному разделу не выставлять: предупреждение о том, чего не
  проверяли, — это тот же ложный факт.

**Ловушка.** Схема сверяется клиентом. После правки обязателен вызов через настоящий
клиент, а не только юнит: ответ `-32602` или `-32600` означает, что структура разошлась со
схемой.

**Проверка.** Три стенда × два раздела. Ожидается: на alpine и debian разделов `services`
и `updates` в ответе нет, а в `unavailable` — по строке с причиной; на стенде, где systemd
работает, всё как прежде. Плюс живой вызов через клиент — ошибок протокола нет.

### 5. Снимок не объявляет отсутствие служб (MCP-07)

**Что не так.** `ssh_snapshot` на `mcp-debian` печатает «No active services detected», хотя
systemd не отвечает. На alpine и router, где `systemctl` нет вовсе, тот же снимок отвечает
честно: «NOT CHECKED: no systemctl on the server».

**Точка правки.** `src/tools/snapshot-tool.ts:202-206` — проверяется наличие двоичного
файла (`command -v systemctl`), а не то, отвечает ли systemd. Дальше `:211`
(`systemctl is-active … || echo inactive`) превращает отказ в «служба не запущена», и
печать сводит это к «No active services detected» (`:503`).

**Границы.**
- Ветку «нет systemctl» не переписывать — она работает.
- Добавляется третий исход, а не заменяется существующий: «systemctl нет», «systemd не
  ответил», «службы опрошены». Два первых — «NOT CHECKED» с разной причиной.
- Формат снимка (рамки, отступы, порядок разделов) не менять.

**Опора.** Тот же `NO_SYSTEMD` из `audit-tool.ts:873`. Если удобнее — вынести образец в
общее место, но тогда обе стороны прогнать заново, а не только новую.

**Проверка.** Три стенда: debian — «systemd did not answer», alpine и router — «no
systemctl», плюс любой стенд с рабочим systemd, где список служб обязан остаться прежним.
Последний замер сторожит, что починка не превратила рабочий случай в «нечем проверить».

### 6. Команда не выполняется, если переход в рабочий каталог не удался (MCP-04)

Самая рискованная задача спринта: правка в одной строке меняет то, как сервер разбирает
**каждую** команду с `cwd`.

**Что не так.** `cwd` подставляется склейкой `cd <каталог> && <вся строка>`, а `&&`
связывает только ближайшую команду. Всё после `;` выполняется независимо от того, удался
переход или нет — в домашнем каталоге, и с кодом возврата 0.

```
ssh_exec { cwd: "/nonexistent-dir-xyz", command: 'echo "before"; pwd; echo "after"' }
→ sh: 1: cd: can't cd to /nonexistent-dir-xyz
  /root
  after          ← выполнено не там, где просили
  Exit code: 0   ← и объявлено успехом
```

**Точки правки.** `src/managers/ssh-executor.ts:98` (обычный вызов) и
`src/tools/exec-tool.ts:347` (фоновая задача). Обе — одна и та же склейка.

**Направление, а не предписание.** Замером выбрать одно из двух, прежде чем писать код:

1. `cd <каталог> || exit 1; <команда>` — не трогает текст команды и её кавычки вовсе.
2. `cd <каталог> && { <команда>; }` — сохраняет нынешнюю связку, но требует вставки в конец,
   и на команде, кончающейся на `&`, уже была ловушка со скобками в `job-command.ts`.

**Чего делать нельзя.** Заворачивать команду в `sh -c '<команда>'` ради `cwd`. Это меняет
слой, разбирающий кавычки, — тот самый класс §5 CLAUDE.md, на котором прошлый спринт ловил
по одному тильду, шаблон, пробелы, обратный слэш и подстановку. Обёртка уже есть у `sudo`
(`ssh-executor.ts:93`), и вторая поверх неё даст двойное экранирование.

**Границы.**
- Порядок «сначала переход, потом повышение прав» сохраняется:
  `cd … <разделитель> sudo <оболочка> -c '<команда>'`.
- Поведение пакетного вызова уже правильное (каждая команда получает свой переход, отказ
  даёт код 2 и ничего не выполняется) — оно обязано таким и остаться.
- Код возврата при неудавшемся переходе может измениться; какой именно — назвать в отчёте и
  проверить, что он ненулевой во всех трёх формах вызова.

**Ловушка.** Тесты закрепляют нынешнюю склейку дословно:
- `tests/unit/ssh-executor.test.ts:108-120` — `cd '/srv/app' && ls` и
  `cd '/srv/app' && sudo bash -c 'ls'`;
- `tests/unit/exec-detach.test.ts:143-150` — `cd '\''/srv/app'\'' && make build`, где кавычки
  уже удвоены, потому что команда задачи уезжает внутрь `sh -c`.

Второй из них — предупреждение: у фоновой задачи текст проходит ещё один уровень кавычек,
и любой новый знак в склейке этот уровень тоже пройдёт.

**Проверка — семейством, а не одним случаем.** На всех трёх стендах, каждый пункт с
существующим и с несуществующим каталогом:

| Форма вызова | Что сторожим |
|---|---|
| одна команда | не выполняется при неудачном переходе, код ненулевой |
| несколько команд через `;` | не выполняется **ни одна** |
| массив команд | поведение прежнее: код 2, ничего не выполнено |
| `sudo` + `cwd` | порядок обёрток сохранён, права повышаются |
| `detach` + `cwd` | задача не стартует впустую, `exit_code` ненулевой |
| команда с кавычками, `$`, пробелами, тильдой в имени файла | текст доезжает без искажения |
| команда, оканчивающаяся на `&` | запускается, скобки не ломают разбор |
| существующий каталог, все формы | работает ровно как раньше — это главный сторож регрессии |

Последняя строка таблицы важнее остальных: она проверяет, что починка ничего не отняла.

| мутант | почему тест написать нельзя |
|---|---|
| `''` → мусор в `assertJobId` | строка с пробелом не проходит проверку — тот же бросок |
| убрать `.trim()` в `fieldsOf` | краевые пробелы дают пустые токены, их отсекает `separator > 0` |

| `separator > 0` → `>= 0` | токен `=x` даёт поле с пустым именем, его никто не спрашивает |
| `newline >= 0` → `> 0` в тексте вывода | при `newline === 0` маркера в голове нет, до ветки не доходит |
