# FIX_16 — аудит молчит о дырах и шумит на ровном месте

**Статус:** ✅ ЗАВЕРШЁН
**Дата заведения:** 2026-08-16
**Ветка:** `feat/openssh-transport`
**Происхождение:** боевая раскатка на свежем сервере —
ACCEPTANCE_LIVE_04, долги TD-18 и TD-19

---

## Зачем этот спринт

Инструменты впервые работали не по нашему сценарию: голый сервер под брутфорсом, аудит,
закрытие дыр, потом чужая раскатка с контейнерами и фаерволом. Нашлись не мелочи вывода,
а один класс: **сигнал не совпадает с опасностью.**

Аудит промолчал там, где машина стояла беззащитной, и напечатал предупреждение там, где
читался файл. Обе половины одинаково вредны. Молчание читается как «проверено, чисто» —
и свежий сервер уезжает в работу без фаервола. Шум на штатной команде приучает пропускать
предупреждения — и настоящее теряется среди ложных.

Спринт правит пять мест. Все пять найдены на живой машине и подтверждены по коду; ни одно
не додумано «на всякий случай».

## Границы: чего в этом спринте не делаем

- **Имена инструментов и формат профилей не трогаем.** Пакет в npm.
- **Типы полей в схеме ответа не меняем.** Новые флаги — это строки в существующих списках
  `red_flags`, а не новые поля и не смена типов.
- **`fail2ban` не появляется ни в одной рекомендации.** Он банит агента, решение принято.
- **Работающее не сужаем.** Ни одна задача не отнимает возможность, которая есть сегодня.
- **Сторож удаления не трогаем.** Задача 5 — про предупреждения, `destructive-command.ts`
  остаётся как есть, у него своя проверенная логика.
- **Ответ «здесь менять нечего» — законный.** Не воспроизвелось на замере — задача
  закрывается замером, а не правкой.

## Общая процедура каждой задачи

1. **Замер до кода.** Воспроизвести на названном стенде, записать ответ дословно.
   Не воспроизвелось — стоп.
2. **Правка** в названной точке.
3. **Замер после.** Тот же вызов, тот же стенд, ответ дословно.
4. **Юнит на новое поведение** и `npm run mutate -- HEAD` по тронутому.
5. **Пара тестов, а не один.** Правило №4 проекта: у каждой ветки проверяется и срабатывание,
   и молчание. Флаг, который всегда горит, бесполезен ровно так же, как и потухший.
6. **Отчёт задачи — diff и вывод команд**, не слово «сделано».

### Про стенды

Задачи 1, 2 и 5 закрываются лабораторией и юнитами: там разбор текста, живой ufw не нужен.

Задачи 3 и 4 упираются в то, чего в лаборатории нет: `ufw`, работающий systemd, контейнеры
с опубликованными портами. Честный вариант один — стенд поднимается отдельно (контейнер
с `ufw` и docker внутри) либо замер делается на машине, где это уже есть, **только чтением**.
Придумывать вывод команд руками нельзя: правило №6 проекта, и именно на выдуманном моке
такие проверки уже один раз оказались зелёными впустую.

## Замеры «до» и решения, принятые на старте

Стенды разошлись с ожиданием, поэтому здесь записано, чем какая ветка закрывается.

**prod-host, `ssh_audit_baseline` с `ssh+net+firewall+docker`:**

```
red_flags: {"critical":[],"warning":[],"ok":[]}
sshd:      port 2222, passwordauthentication no, permitrootlogin without-password
listeners: 0.0.0.0:2222 sshd  (порт сходится — сокета больше нет, стоит ssh.service)
ufw:       Status: active, Default: deny (incoming), 6 правил
iptables:  199 строк, INPUT policy DROP
nat/DOCKER: -N DOCKER  (контейнеры в host-режиме, публикаций нет)
```

Пустой `red_flags` целиком — задача 3 в чистом виде: про включённый экран не сказано
даже строкой в `ok`.

**prod-host, стенд задачи 4** (контейнер с публикацией портов поднят и снесён, порт закрыт):

```
-A DOCKER ! -i docker0 -p tcp -m tcp --dport 19999 -j DNAT --to-destination 172.17.0.2:80
-A DOCKER ! -i docker0 -p tcp -m tcp --dport 19998 -j DNAT --to-destination 172.17.0.2:81
```

**Лаборатория:** `iptables` и `ufw` нет ни на одном контейнере (`NO_IPTABLES`, `NO_UFW`) —
это готовая ветка «экрана нет вовсе». `ss` и `netstat` есть только на alpine, значит стенд
для сверки портов (задача 2) — alpine.

**Решения:**

- Флаг паролей теряет порт совсем: `PasswordAuthentication yes`. Одно утверждение — один
  источник; порт печатается в разделе `sshd` и в предупреждении о расхождении (TD-18).
- Наличие экрана определяется политикой цепочки `INPUT`, а не числом строк `iptables -nL`.
  199 строк на prod-host — это цепочки ufw и docker, из счётчика вывод о защите не следует.
  Поле `rules` в схеме остаётся как есть, политика читается отдельной командой раздела.
- Цепочка docker читается как `iptables -t nat -S DOCKER`: пустая отвечает ровно `-N DOCKER`,
  а правила приходят строкой с `--dport`, которую не нужно разбирать по колонкам.
- SQL-шаблоны (задача 5) срабатывают, когда в команде есть вызов клиента БД, — тогда
  ищутся по всему тексту. Так ловится и `psql -c "…"`, и heredoc, а `echo TRUNCATE` молчит.
  Клиентов БД на prod-host нет, ветка закрывается юнитами.

## 📊 ЗАДАЧИ

Порядок: сначала то, из-за чего дыра остаётся невидимой, потом шум.

### 1. Нестандартный порт больше не глушит критичный флаг

**Что не так.** Условие требует одновременно «пароли разрешены» **и** «порт равен 22»:

```ts
if (/^yes$/i.test(result.ssh.password_auth) && /^22$/.test(result.ssh.port))
  result.red_flags.critical.push('PasswordAuthentication yes on port 22');
```

Сервер с паролями на порту 2222 не получает критичного флага вовсе. Аудит отвечает «чисто»
машине, куда можно войти по паролю. Перенос SSH на нестандартный порт — первое, что делают
при настройке, то есть глушится ровно на тех машинах, которые кто-то уже трогал руками.

На боевой машине флаг сработал случайно: `sshd -T` отдал 22, потому что порт держал
`ssh.socket`. Совпадение спасло — а не логика.

**Точка правки.** `audit-tool.ts:443-444`.

**Что должно стать.** Разрешённый пароль критичен сам по себе, независимо от порта. Порт —
подробность в тексте, а не условие срабатывания. Нестандартный порт не защита: он снижает
объём мусорного перебора, но не мешает войти тому, кто адрес и порт уже знает.

**Пара тестов.** Пароли `yes` на 22 → флаг. Пароли `yes` на 2222 → флаг. Пароли `no` на
22 → флага нет. Третий обязателен: без него условие «всегда критично» тоже зелёное.

---

### 2. Порт в ответе сверяется с тем, кто слушает на самом деле

**Что не так.** Порт берётся из `sshd -T`, а фактические слушатели лежат в соседнем разделе
того же ответа — и между собой они не сверяются. На Ubuntu 22.04+ порт задаёт `ssh.socket`,
и `sshd_config` с ним расходится молча.

Живой пример: ответ утверждал `on port 22`, а в его же `net.listeners` стоял `0.0.0.0:2222`.

Обратный случай опаснее, и он не гипотетический: в конфигурации нестандартный порт,
а слушается 22 — открытый 22 остаётся невидимым, потому что аудит поверил конфигурации.

**Точка правки.** `audit-tool.ts:371-379` (сборка) и классификация ниже.

**Что должно стать.** Когда собраны оба раздела и они расходятся, это отдельное
предупреждение: сказано одно, слушается другое. Не «исправить» одно значение другим —
расхождение и есть находка, скрывать его нельзя.

**Ловушка.** Разделы независимы: `net` могли не запросить. Нет второго раздела — сверки
нет, и молчание здесь правильное, а не пропущенный флаг.

**Пара тестов.** Совпало → тишина. Разошлось → предупреждение. Раздела `net` нет → тишина.

---

### 3. Отсутствие фаервола становится находкой

**Что не так.** Раздел `firewall` собирается, печатается — и не участвует в классификации
ни одной строкой. Машина с выключенным `ufw`, политикой `ACCEPT` и нулём правил получает
пустой список замечаний по этой части.

Именно так выглядел свежий сервер: фаервола нет вовсе, а в красных флагах — тишина. Дыру
нашли глазами в разделе, не по сигналу.

**Точка правки.** `audit-tool.ts:434-456`, рядом с остальной классификацией.

**Что должно стать.** Три исхода раздела уже различаются кодом (`not_installed`,
`no_access`, посмотрели) — на них и опереться:

| Состояние | Сигнал |
|---|---|
| `ufw` выключен или не установлен и правил `iptables` нет | предупреждение: входящее не ограничено |
| «посмотреть не дали» | остаётся в `unavailable`, флага нет |
| экран включён | строка в `ok` |

**Почему предупреждение, а не критично.** Машина за внешним фаерволом провайдера или в
закрытой сети живёт без своего экрана штатно. Критичность здесь означала бы крик на
нормальной конфигурации — та самая ошибка, которую чиним в задаче 5.

**Пара тестов.** Выключен → предупреждение. Включён → `ok`. Не дали посмотреть → ни того,
ни другого.

---

### 4. Docker мимо фаервола перестаёт быть невидимым

**Что не так.** Смотрится только таблица `filter` (`iptables -nL`). Docker публикует порты
правилами в `nat`, в цепочке `DOCKER`, и они срабатывают **раньше** пользовательских правил
`ufw`. Обычный итог: `ufw status` показывает `deny (incoming)`, а порт контейнера открыт
всему интернету. Аудит в этом случае честно печатает «экран включён» — и это правда,
которая вводит в заблуждение.

Проверка на боевой машине показала, что там цепочка пуста (контейнеры в режиме хоста),
то есть обхода нет. Но узнали это отдельной командой руками — аудит про такое не спрашивает.

**Точка правки.** `audit-tool.ts:245-252` (команда раздела) и классификация.

**Что должно стать.** Когда на машине есть и docker, и включённый экран, дополнительно
смотрится `iptables -t nat -L DOCKER`. Непустая цепочка при `deny incoming` — предупреждение
с перечислением опубликованных портов: экран включён, но эти порты идут мимо него.

**Границы.** Только чтение. Ничего не чинить и не советовать «добавьте правило» — инструмент
докладывает, решение за человеком. Нет docker — команда не выполняется вовсе, лишнего RTT
на машинах без него не появляется.

**Пара тестов.** Цепочка непустая при включённом экране → предупреждение. Цепочка пустая →
тишина. Docker нет → команда не выполнялась.

---

### 5. Предупреждения ловят команду, а не слово (TD-19)

**Что не так.** `/\breboot\b/` срабатывает на `/var/run/reboot-required`: границы слова не
спасают, слева слэш, справа дефис. Ничего не выполняется — читается файл. Тот самый файл,
который читает наш же `ssh_audit_baseline` (`audit-tool.ts:260`), то есть предупреждение
звучит на действии, которое инструменты делают сами и постоянно.

Тем же болеют `halt`, `shutdown`, `TRUNCATE`.

**Точка правки.** `exec-tool.ts:28-54`.

**Что должно стать.** Проверяется имя в позиции команды, а не подстрока где угодно. `reboot`
первым словом — вызов; `reboot` внутри пути, аргумента или строки в кавычках — нет. Разбор
для этого в проекте уже написан, он живёт в стороже удаления, и заводить второй не нужно.

**Почему это не косметика.** Прямо над списком записано, почему из него убрали удаление:
шаблон кричал на любом абсолютном пути, а предупреждение, звучащее на штатной работе,
перестают читать. Для `rm` вывод сделали, остальной список оставили — вернулось тем же боком.

**Пара тестов на каждый шаблон.** Вызов: `reboot`, `shutdown -r +1`, `halt`. Упоминание:
`test -f /var/run/reboot-required`, `grep reboot /var/log/syslog`, `echo halt`. Первая
группа обязана предупредить, вторая — промолчать.

## Что получилось

Все пять задач закрыты, каждая — замером на живой машине, а не только юнитом.

| Задача | Проверено на | Ответ после правки |
|---|---|---|
| 1. Порт не глушит флаг паролей | alpine, пароли `yes` на порту 2222 | `CRITICAL: PasswordAuthentication yes` |
| 2. Сверка порта со слушателями | там же, конфигурация 2222 против слушателя 22 | `WARNING: sshd config says port 2222, but sshd listens on 22` |
| 3. Фаервол в классификации | prod-host / alpine / debian | `ok` — `firewall active (ufw)`; предупреждение — экрана нет; молчание — смотреть не дали |
| 4. Docker мимо экрана | prod-host, контейнер с `-p 19999:80 -p 19998:81` | `WARNING: docker publishes port(s) 19999, 19998 past the firewall` |
| 5. Предупреждение о команде | alpine, свежая сборка | чтение `reboot-required` молчит, `timeout 5 poweroff` предупреждает |

**Решения, принятые по ходу и подтверждённые замером:**

- Политика цепочки `INPUT` вместо счётчика правил: 199 строк на prod-host — это цепочки ufw и
  docker, вывода о защите из числа не следует.
- Ветка `policy REJECT` убрана: ядро такой политики не принимает («Bad policy name»).
- Разделители shell режут команду только вне кавычек. Без этого `git commit -m "fix; reboot
  handler"` давал вызов `reboot` — ложная тревога в новой форме.
- Обёртки (`timeout`, `nice`, `env`, `nohup`, `setsid`, …) пропускаются вместе со своими
  аргументами: старый поиск подстроки ловил `timeout 5 reboot`, разбор по первому слову —
  нет, и охват сузился бы.

**Известная граница — снята в FIX_17.** `sudo -u deploy reboot` не распознавался: значение
флага обёртки было неотличимо от имени команды. Карта «обёртка → её флаги» это различие
вернула, и форма отказывается наравне с остальными — проверено живьём на обоих контейнерах
под пользователем `deploy` (2026-08-16).

## Замечено рядом, в этот спринт не входит

- `net.listeners` собирается и ни на что не влияет: служба, торчащая наружу на `0.0.0.0`,
  сама по себе не даёт ни флага, ни строки в `ok`. Задача 2 использует раздел только для
  сверки с портом SSH — общий разбор слушателей это отдельная работа.
- Контейнерные журналы недоступны, когда у docker выбран драйвер логов без чтения
  (`docker logs` отвечает отказом). Диагностика в этом случае идёт вслепую. Нашего кода
  не касается, но стоит знать при следующем разборе.
