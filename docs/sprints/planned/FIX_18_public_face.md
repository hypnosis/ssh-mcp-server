## Волна 3 — типизировать вход инструментов ✅

Идёт после волны 2: те же файлы, иначе правки столкнутся.

Четырнадцать мест вида `const args = request.params.arguments as any`. В проекте уже
есть `src/utils/tool-args.ts` — разбор переезжает на него. Остальные 78 `any` не
трогаются, кроме случаев, где замена очевидна и ничего не меняет по смыслу.

Файлы по убыванию: `job-tools.ts` (4), `audit-tool.ts` (4), `file-tools.ts` (3),
`transfer-tool.ts` (2), `log-tools.ts` (2), по одному — `snapshot-tool.ts`,
`monitoring-tool.ts`, `exec-tool.ts`, `profiles-file.ts`.

**Проверка:** `tsc --noEmit` чист; юниты зелёные; на каждый тронутый инструмент —
живой вызов на контейнере лаборатории, потому что типизация входа меняет разбор
аргументов, а юниты на моках повторят ошибку кода. `npm run mutate -- HEAD` по
тронутому: выживший мутант в свежем коде означает недописанный тест.

### Как сделано

Восемнадцать мест, а не четырнадцать: цифра в плане была занижена, а `profiles-file.ts`
попал в список ошибочно — там `data as any` при разборе файла профилей, к аргументам
инструмента отношения не имеет. Его не трогали.

`src/utils/tool-args.ts` не менялся: трёх его функций хватило. Заменялась только сама
строка получения аргументов. Рядом с каждым обработчиком объявлен локальный интерфейс по
образцу его `inputSchema`:

```ts
const args = (request.params.arguments ?? {}) as ExecArgs;
```

Восемь интерфейсов: `BaselineArgs`, `TlsCheckArgs`, `DiskBreakdownArgs`,
`ServiceStatusArgs`, `ExecArgs`, `FileReadArgs`/`FileWriteArgs`/`FileListArgs`, `JobArgs`,
`LogArgs`, `MonitorArgs`, `SnapshotArgs`, `UploadArgs`/`DownloadArgs`.

**Приём не сужен, и это главное.** Поле, у которого есть собственная проверка, объявлено
`unknown` — `command`, `path`, `pattern`, `query`, `mode`, `owner`, `timeout` у передачи.
Строгий тип стоит только там, где код и раньше читал значение напрямую. В рантайме
приведение стирается, поэтому вызов, который проходил до правки, проходит и после.

Что даёт замена: опечатка в имени поля теперь ошибка компиляции, а `Record<string,
unknown>` её бы не поймал.

**Побочный эффект `?? {}`.** Вызов без `arguments` вовсе (все поля инструмента
опциональны) раньше падал сырым `TypeError` на `args.profile`. Теперь берётся профиль по
умолчанию — ровно то, что обещает схема. Изменение в сторону расширения, не сужения.

Два места в `audit-tool.ts` держат собственный текст отказа (`Invalid domain:`,
`Invalid unit name:`), их тесты сверяют дословно — они не переехали на `requireText`,
там точечное `as string` перед той же проверкой.

**Мутации.** Скрипт умеет мерить только всю незакоммиченную ветку целиком — сорок восемь
файлов, включая волны 1 и 2. Выживших мутантов на коде волны 3 нет. Ценность этого замера
невелика: приведение типа стирается при сборке, мутировать в нём нечего, и мутанты там
эквивалентны по определению. Настоящим сторожем здесь была живая сетка.

## Порядок и агенты

Модель для всех задач — **sonnet**: работа механическая и проверяемая диффом.

```
Волна 1  ──  восемь агентов сразу, файлы не пересекаются
             (1.1 первой — имена машин)
                     │
Волна 2  ──  пять агентов, каждому свой каталог
             (проверка после каждого куска, не в конце)
                     │
Волна 3  ──  один агент, последовательно по файлам
             (живой прогон на лаборатории обязателен)
```

Волна 1 не ждёт ничего. Волна 2 может идти параллельно волне 1 — пересечение только
по `src/index.ts` (задача 1.2 и кусок 2.3), поэтому кусок 2.3 берётся **после** 1.2.

### Что кладём в промпт каждому агенту

Правила проекта агент не видит: ни `CLAUDE.md`, ни хуки, ни эту память. Без явных
слов он достроит недостающее сам и ошибётся.

- **Один агент — один каталог, список файлов в промпте.** Правило «один агент — один
  файл» ослаблено сознательно: правки механические, а дифф каталога читается целиком.
- **Разведка — через `mcp__lumen__semantic_search`, а не grep по дереву.** Без этой
  строки агент идёт грепать.
- **Доказательство — `file:line`.** Пересказ своими словами не проверяется никак.
- **Право ответить «менять нечего».** Формулировка «„всё сходится“ — нормальный ответ»
  экономит целый разбор.
- **Границы языка:** переводим комментарии в `src`; `docs/`, `tests/` и строковые
  литералы не трогаем.
- **Оговорку «не трогай то, что нарушает правило» надо ограничивать примером.** Это
  стоило двух переделок, см. ниже.
- **Запрет на попутные улучшения.** Заметил рядом мёртвый код или плохой комментарий —
  называет в отчёте, не удаляет.

Отчёт агента не заменяет проверку: верим диффу и прогону, а не тексту «сделано».

### Чему научили волны

**Оговорка без примера читается шире, чем задумана.** В задание на перевод я вписал:
«комментарий, который сам нарушает правило проекта, не переводи, выпиши в отчёт —
удаление решает владелец». Имелись в виду редкие блоки на выброс. Два агента из шести
поняли иначе и оставили по-русски всё, где встречалось слово «замерено»: 47 и 25 строк,
причём у второго — в JSDoc публичного интерфейса `SSHConfig`, то есть ровно в витрине
пакета, которую то же задание называло главной. Формально оба выполнили инструкцию.

Формулировка, которой не хватало и которая всё починила: **факт о поведении системы
остаётся, ссылка на то, как мы этот факт узнали, уходит.** «coreutils возвращает 124,
BusyBox — 143» остаётся; «(замерено на контейнерах)» рядом уходит. Туда же — цифры,
приведённые как доказательство, рассказ о прошлом состоянии кода и ссылки на спринты.

**Уточнять надо всем сразу, а не только споткнувшимся.** Трое ещё работали с той же
формулировкой. Сообщение вдогонку сэкономило две переделки из трёх.

**Агент нашёл собственную ошибку на втором заходе.** При первом проходе он выбросил
целый абзац в `logger.ts` — не перевёл и не оставил. Заметил сам, восстановил. Отсюда
проверка, которую стоит гонять после любой массовой правки комментариев: сравнить число
строк-комментариев в `HEAD` и в рабочем дереве по каждому файлу. Уменьшилось — иди
смотреть глазами. Из 50 файлов сократился один, и ровно там, где сокращение планировали.

**Агенты пугаются чужих правок в рабочем дереве.** При параллельной работе пятеро из
семи отдельно предупредили, что видят посторонние изменения, и уточнили, что не трогали
их. Строка «параллельно работают другие агенты, чужие изменения не откатывай» экономит
этот абзац в каждом отчёте.

**Дважды агент опроверг мой «установленный факт», и оба раза был прав.** Русский текст
нашёлся ещё и в `test.yml`, а имя боевой машины — в третьем месте вместо двух названных.
Строка «факты проверены, но ссылки сверь» окупается.

**Третий раз — там же, в волне 3.** В плане стояло «четырнадцать мест», в списке файлов
значился `profiles-file.ts`. На деле мест оказалось восемнадцать, а `profiles-file.ts`
попал в список по совпадению слова `any`: там разбор файла профилей, другой поток
данных. Агент замерил, вынес расхождение в отчёт и файл не тронул — то есть сделал ровно
то, что просило разрешение «ответ „здесь менять нечего“ законный». Список файлов,
собранный грепом по общему признаку, требует проверки перед тем, как попасть в задание.

## Готовность

Спринт считается закрытым, когда одновременно верно:

```bash
git grep -c '[а-яА-Я]' -- src                              # 0   ✅ сходится
grep -rl '[а-яА-Я]' dist | wc -l                           # 0   ✅ сходится (после npm run build)
git grep -InE 'prod-a|prod-b|prod-c|prod-d'      # пусто ✅ сходится
npm pack --dry-run | grep -c '\.map'                       # 0   ✅ сходится
npx tsc --noEmit                                           # чисто ✅ сходится
npx vitest run tests/unit/                                 # 2157, зелено ✅ сходится
git grep -c 'request.params.arguments as any' -- src       # 0   ✅ сходится
SSH_MCP_LIVE=1 npx vitest run tests/live/                  # 307, зелено ✅ сходится
```

Все восемь сошлись 2026-08-17. Осталось одно необратимое действие — коммит, он за
владельцем.

Живая сетка обязательна: волна 3 меняет разбор аргументов инструментов, а юниты на
моках повторяют ошибку кода — правило №1 проекта инструментами не заменяется.

Прогон живой сетки — строго по одному за раз. Тесты отмены считают процессы на
контейнере глобально по метке, зависящей только от его порта, поэтому два одновременных
прогона на одной машине валят друг друга и дают ложные падения.
