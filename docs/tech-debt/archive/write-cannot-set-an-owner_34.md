# TD-34. Записать файл можно, назначить ему владельца — нет

**Дата:** 2026-08-23
**Статус:** ✅ ЗАКРЫТ 2026-08-23 — [CORE_24](../sprints/archive/CORE_24_words_and_owner.md)
**Откуда:** круг проб на чистых агентах 2026-08-23, задачи «положи конфиг» и «залей сборку»

---

## Что происходит

У `ssh_upload` есть параметр `owner`: «"root:root", every file sent. Needs sudo; without it
the answer says it was not applied». У `ssh_file_write` такого параметра нет вовсе. Права
он ставит (`mode`), владельца — нет.

Разрыв заметили оба агента, независимо друг от друга. Дословно: «у `ssh_upload` есть
`owner`, у `ssh_file_write` такого поля нет вовсе. Кто окажется владельцем после записи под
sudo — из текста не следует. Если nginx требует конкретного владельца, понадобится
отдельный `ssh_exec chown`, и это уже дырка в „одном вызове"».

## Почему это долг, а не придирка

Запись под `sudo` идёт в `/etc`, `/opt` и прочие места, где владелец значит ровно столько
же, сколько режим доступа. Инструмент, который ставит режим и молчит про владельца,
оставляет работу наполовину — и остаток приходится делать через `ssh_exec`, то есть ровно
тем способом, от которого весь набор и уводит.

Второй агент назвал и следствие: раз владельца назначить нечем, ответ про него ничего не
говорит, и проверять приходится отдельным `ssh_file_list`.

## Что решить в спринте

- Добавлять ли `owner` в объект файла у `ssh_file_write` — по образцу `ssh_upload`, включая
  ответ «просили владельца, но без `sudo` он не применён».
- Порядок: у `mode` сказано «applied before the file takes its place», и владелец обязан
  вставать туда же — иначе между постановкой на место и `chown` есть окно, в котором файл
  виден под чужим владельцем.
- Отдельный вопрос к `ssh_upload`: `owner` описан как «every file sent», и про каталоги в
  дереве не сказано ничего. Агент заметил, что без прохода по каталогам nginx файлы не
  отдаст, и добавил в план проверку глазами.

---

## Чем закрыт

`owner` есть у `ssh_file_write`, по образцу `ssh_upload` и с той же формулировкой отказа —
она теперь одна на оба инструмента (`OWNER_NEEDS_SUDO` в `transfer-output.ts`).

- Владелец ставится на площадке, после прав и до переименования: окна, в котором файл виден
  под чужим владельцем, нет. Порядок проверяется тестом по индексам команд.
- Без `sudo` файл всё равно встаёт на место, а ответ несёт «owner was NOT applied» —
  отказывать было бы хуже: работа сделана, не сделана только её часть.
- Имя владельца проверяется `shellOwner` до первой команды на сервере.
- Живьём на обоих контейнерах: `tests/live/sudo-path.live.test.ts`, пара «поставлен под
  sudo» и «без sudo не выдан за поставленного». Мутация «не отправлять chown» красит оба.

Третий пункт записи тоже закрыт: `owner` у `ssh_upload` говорит «every file and directory
sent» — при `recursive` chown идёт с `-R`, и каталоги он задевает наравне с файлами.
