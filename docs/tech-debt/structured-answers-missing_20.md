# TD-20. Половина ответов разобрана, половина — текст, и различить заранее нельзя

**Дата:** 2026-08-18
**Статус:** 🔹 отложено, решение владельца 2026-08-18
**Откуда:** CORE_19, разбор поверхности MCP

---

## Что есть сейчас

`ssh_audit_baseline` и `ssh_tls_check` объявляют схему ответа и отдают поля рядом с
текстом (`src/tools/audit-output.ts`, `src/tools/audit-tool.ts:105,129`). Клиент сверяет
пришедшее с объявленным, поэтому схема — обещание, а не описание: расхождение возвращается
ошибкой протокола вместо ответа.

В CORE_19 к ним добавляются `ssh_disk_breakdown` и `ssh_service_status` — семейство аудита
станет однородным.

## Что остаётся текстом

| Инструмент | Что было бы полями | Почему отложено |
|---|---|---|
| `ssh_snapshot` | секции обзора | Дорого: каждая секция должна уметь сказать «проверить нечем» отдельно, а обзор читают целиком. Плюс поля едут **вместе** с текстом, а не вместо — обзор ушёл бы агенту дважды |
| `ssh_job_status`, `ssh_job_list` | состояние из трёх, код возврата, pid, время старта | Три исхода (`running`, `finished`, `lost`) сейчас различимы только по тексту, а `lost` — ни успех, ни провал |
| `ssh_upload`, `ssh_download` | исход сверки, sha256, размер | Три исхода сверки (сошлось / не сошлось / нечем) агент разбирает глазами, а по ним принимается решение сносить уехавшее |
| `ssh_monitor` action `test` | состояние из четырёх | Сейчас состояние — первое слово строки; полем оно не ошибалось бы при пересказе |

## Чего здесь сознательно нет

Файловые и журнальные инструменты. Их ответ — само содержимое файла или строки журнала;
поля поверх него ничего не добавляют, а размер ответа удваивают.

## Когда возвращаться

Каждая строка таблицы — самостоятельная работа, ни одна не блокирует другую. Кандидат
первой очереди — передача: там исход сверки уже сегодня определяет, снесёт ли установщик
уехавшее дерево, и цена неверно прочитанного текста самая высокая.
